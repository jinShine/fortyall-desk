## 1. 배경과 목표

### 최종 목표
개발자 본인이 **백엔드 개발자로 취업**하는 것. 프로젝트는 그 수단이자 포트폴리오다.
따라서 "동작하는 결과물"과 "설명할 수 있는 역량"을 동시에 만든다. 둘 중 하나만 남으면 실패다.

### 9/12 시점의 완성 정의
실제 도메인으로 접속되는 서비스가 AWS에서 돌아가고, 아래 코어 루프가 끝까지 동작한다.

```
센터 개설 → 회원 등록 → 수업권 발급 → 고정 스케줄 등록
         → 레슨 자동 생성 → 예약 → 출석 → 원장 조회
         → 관리자 처리 큐 → 알림
```

9/12 이후는 테스트와 디테일 보완에 쓴다.

## 2. 확정된 결정

브레인스토밍에서 합의한 네 가지다. 이 문서의 나머지는 전부 여기서 파생된다.

### 2.1 역할 분담 — 프론트엔드는 AI가 전담
개발자는 백엔드만 작성한다. 프론트엔드는 100% AI가 담당한다.

**작업 방식**: 도메인 단위 수직 슬라이스. 예를 들어 회원 도메인을 할 때 화면과 API를 함께 올리고,
화면이 요구하는데 API에 없는 필드가 발견되면 그 자리에서 기획을 보완한다.

**근거**: 개발자는 프론트엔드 경력자라 프론트에서 배울 것이 없다. 학습 시간을 백엔드에 몰아준다.
동시에 화면이 API 요구사항을 끌어내므로 설계 누락이 조기에 드러난다. (기획서 12장 수직 슬라이스 원칙)

### 2.2 기능 범위 — 코어 루프 + 처리 큐 + 알림

**포함**: 인증·센터·회원·상품·수업권 원장·고정 스케줄·Materializer·예약·출석·결번·관리자 처리 큐·알림

**제외**: NTRP · CSV 일괄 등록 · 홀드 · 선결제 승계 · 알림톡 · 온라인 결제(PG)

**구조는 지원하되 기능은 만들지 않는 것**: 2인 레슨과 홀드.
ERD의 `ScheduleParticipant` · `RecurringEnrollment` 구조가 이미 두 경우를 표현할 수 있으므로
테이블과 엔티티는 그대로 만든다. 다만 2인 등록 화면과 홀드 처리 API는 이번 범위 밖이다.
D11에서 이 두 가지를 반례로 다루는 것은 테이블 경계를 이해하기 위한 것이지 기능 구현이 아니다.

진행 중 필요가 확인되면 추가한다.

### 2.3 교수 방식 — 전부 직접 타이핑

개발자가 모든 백엔드 코드를 직접 타이핑한다. AI는 개념 설명, 힌트, 코드 리뷰를 담당한다.

**대가**: 속도가 절반 이하로 떨어진다. AI가 작성하면 하루에 끝날 일이 이틀 걸린다.
이 위험은 인지된 상태에서 선택되었으며, 4.3의 재조정 규칙이 안전장치다.

**완화**: 반복적인 구간(DTO, 단순 CRUD 컨트롤러, 매핑 코드)은 개발자가 요청하면 AI가 대신 작성한다.

### 2.4 테스트 전략 — 불변식만

돈 사고가 나는 지점에만 테스트를 쓴다. 총 20~30개 수준.

| 대상 | 검증할 것 |
|---|---|
| 수업권 원장 | 발급·차감·복구·조정 후 잔여가 트랜잭션 합과 일치 |
| 동시 예약 | 같은 슬롯에 동시 요청 시 한 명만 성공 |
| QR 중복 스캔 | 2회 차감되지 않음 |
| 결제 승인 중복 | Pass가 1개만 발급됨 |
| Materializer | 중복 실행해도 레슨 1개 |
| 테넌트 격리 | 타 센터 데이터 접근 차단 |

**근거**: 전면 TDD는 "전부 직접 타이핑"과 겹치면 22일 안에 범위를 못 맞춘다.
면접에서는 테스트 개수보다 "어디에 왜 테스트를 썼는가"의 판단이 평가된다.

## 3. 전략 — 수직 슬라이스 + Walking Skeleton, 슬라이스는 어려운 것부터

### 3.1 배포를 맨 앞에 둔다

신규 프로젝트에서 실무가 가장 먼저 하는 일은 기능이 아니라 **빈 껍데기를 프로덕션까지 흘려보내는
파이프라인을 뚫는 것**이다. 배포·인증·로깅처럼 나중에 끼워 넣기 고통스러운 것들이 여기서 걸러진다.

이 프로젝트에 특히 맞는 이유: **Docker · CI/CD · AWS가 전부 처음**이다.
처음 하는 일은 반드시 예상보다 오래 걸린다. 3주차에 만나면 되돌릴 시간이 없고,
1주차에 만나면 남은 2주가 완충재가 된다.

**대가**: W1에는 도메인 진도가 사실상 나가지 않는다. 기능은 로그인 하나뿐인 채로 한 주가 끝난다.

### 3.2 슬라이스 순서는 어려운 것부터

| 순서 | 슬라이스 | 배치 근거 |
|---|---|---|
| 1 | 인증·센터·회원 | 모든 것의 전제. 테넌트 격리를 여기서 못 잡으면 뒤가 전부 뚫린다 |
| 2 | 수업권 원장 | 프로젝트의 심장. 트랜잭션·정합성 학습 |
| 3 | 고정 스케줄 + Materializer | 배치·멱등성 |
| 4 | 예약 + 동시성 | 락·유니크 제약. 가장 어렵고, 1~3의 기초가 있어야 이해된다 |
| 5 | 출석·결번 | 앞의 응용 |
| 6 | 처리 큐·알림 | 조회 위주. 가장 쉽다 |

**뒤로 갈수록 쉬워지는 배치**다. 마감이 다가올수록 남은 일이 가벼워져 회복이 가능하다.
반대 순서면 마지막 주에 동시성을 만나 무너진다.

### 3.3 검토했으나 채택하지 않은 대안

**계층 우선(Layer-first)** — 엔티티 전부 → 리포지토리 전부 → 서비스 전부.
마지막까지 동작하는 것이 없고 통합에서 문제가 폭발한다. 기획서 12장이 명시적으로 금지한다.

**도메인 먼저, 배포는 중반** — 초반 성취감은 크지만 배포 실패 시 대응 시간이 없다.
개발자 본인이 로드맵에 "배포는 미룰수록 지옥이 된다"고 적어둔 것과 배치된다.

### 4.3 재조정 규칙

계획대로 되지 않는 것이 정상이다. 밀렸을 때 무엇을 버릴지 그 자리에서 정하면 반드시 잘못 고른다.
미리 정해둔다.

**버리는 순서 (위에서부터)**

1. 문자 실발송 연동 → 콘솔 mock 유지
2. 웹푸시 → 인앱 알림함만
3. 처리 큐 항목 7종 → 2종 (결제 확인 · 미처리 레슨)
4. 결번 5종 → 3종 (출석 · 사전취소 · 노쇼)
5. 프론트 화면 축소 (AI 담당이라 개발자 시간에는 영향 없음)

**절대 버리지 않는 것**

- 수업권 원장(Ledger)
- 동시성 제어
- AWS 배포 + CI/CD
- 불변식 테스트
- k6 측정 (시나리오는 하나로 줄여도 됨)

이 다섯이 포트폴리오의 전부다. 기능 개수는 평가 대상이 아니다.

**판정 시점**: 매주 금요일 회고 (D07 · D14 · D21). 그 자리에서 위 목록을 위에서부터 잘라낸다.

## 5. 리스크

### R1. "전부 직접 타이핑"과 22일이 서로 당긴다 — 높음
AI가 작성하면 하루에 끝날 일이 이틀 걸린다. 그것이 학습의 값이며 의도된 선택이다.
**완화**: 4.3 재조정 규칙. 반복 구간은 개발자가 AI에게 위임.

### R2. D05~D06(AWS·CI/CD)이 최대 변수 — 높음
처음 하는 작업이며 이틀로 잡았으나 사흘이 될 수 있다.
**완화**: 밀리면 D07의 도메인·HTTPS를 W2로 넘기고 진도를 이어간다. 배포 자체는 미루지 않는다.

### R3. 12시간 × 22일은 지속 가능하지 않다 — 중간
첫 주는 가능하다. 3주차에 집중력이 떨어지는 것이 정상이며, 그때가 부하테스트 주간이다.
**완화**: 일요일 반나절을 비워둘 것을 권고한다. 계획에는 넣지 않았으나 실제로 필요할 가능성이 높다.

### R4. AWS 과금 — 중간
프리티어는 12개월 한정이며 RDS·EC2를 켜둔 시간만큼 과금된다. Route 53 호스팅 영역도 월 $0.50다.
처음 쓰면 인스턴스를 끄는 것을 잊거나, 프리티어 대상이 아닌 사양을 고르기 쉽다.
**완화**: D05에 예산 알림(Budgets)을 먼저 설정한다. 인스턴스 사양은 프리티어 대상인지 확인하고 고른다.
9/12 이후에도 띄워둘 것을 전제로 월 고정비를 계산해둔다.

### R5. 프론트·백 동시 작업의 통합 비용 — 낮음
화면과 API를 함께 올리면 인터페이스 불일치로 시간이 샐 수 있다.
**완화**: 슬라이스 시작 시 API 응답 형태를 먼저 합의하고 화면을 붙인다.
