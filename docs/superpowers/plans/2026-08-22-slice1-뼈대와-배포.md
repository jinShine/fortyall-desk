# 슬라이스 1 — 뼈대와 배포 파이프라인 (D01~D07)

> **실행 방식:** 이 계획은 AI 에이전트가 아니라 **개발자 본인이 직접 타이핑**한다.
> 각 태스크는 목표·검증 방법·리뷰 포인트를 정확히 명시하되 **구현 코드는 주지 않는다.**
> 막히면 "힌트 줘"라고 요청한다. 힌트는 단계적으로 준다 — 답을 바로 주지 않는다.
> 커밋 명령은 적혀 있으나 **개발자가 직접 실행**한다.

**목표:** `git push` 한 번으로 AWS에 자동 배포되고 `https://www.fortyall.net` 으로 접속되는 서비스를 만든다.

**아키텍처:** Walking Skeleton. 기능은 로그인 하나만 있는 상태로 배포 파이프라인을 먼저 완성한다.
EC2 한 대에 Docker로 앱을 띄우고, Nginx가 앞에서 TLS를 종료한다. DB는 RDS(MySQL)를 쓴다.
GitHub Actions가 테스트 → 이미지 빌드 → ECR push → EC2 재기동까지 처리한다.

**기술 스택:** Spring Boot 3.5.16 · Java 21 · Spring Data JPA · MySQL 8.4 · Docker · GitHub Actions · AWS(EC2·RDS·ECR·Route 53)

**설계 문서:** `docs/superpowers/specs/2026-08-22-22일-완성-커리큘럼-design.md`

## 전역 제약

- Spring Boot **3.5.16** 고정. Boot 4로 올리지 않는다 (수강 중인 강의·QueryDSL 예제와 맞추기 위한 의도적 선택)
- Java **21** (toolchain)
- QueryDSL **5.1.0**, `:jakarta` classifier 필수
- 도메인: `www.fortyall.net`. apex는 www로 리다이렉트
- 타임존: `Asia/Seoul` 고정
- 문자셋: `utf8mb4`. DB·JDBC URL·컨테이너 모두
- **모든 조회는 센터 경계 안에서** — 테넌트 격리는 타협 대상이 아니다 (기획서 12장)
- 코드 주석은 두지 않는다. 설계 근거는 `docs/`가 보관한다
- 커밋 메시지에 기획서 절 번호를 인용한다 (예: `feat: 센터 셀프 가입 (기획서 6.1)`)

```java
@DataJpaTest
class MembershipRepositoryTest {

    @Autowired MembershipRepository membershipRepository;
    @Autowired CenterRepository centerRepository;
    @Autowired AccountRepository accountRepository;

    @Test
    void 한_계정이_여러_센터에_소속될_수_있다() {
        Account 윤다리 = accountRepository.save(new Account("01012345678"));
        Center a센터 = centerRepository.save(new Center("A테니스"));
        Center b센터 = centerRepository.save(new Center("B테니스"));

        Membership m1 = new Membership(a센터, "윤다리", "01012345678");
        Membership m2 = new Membership(b센터, "윤다리", "01012345678");
        m1.activate(윤다리);
        m2.activate(윤다리);
        membershipRepository.save(m1);
        membershipRepository.save(m2);

        assertThat(membershipRepository.findAllByAccountId(윤다리.getId())).hasSize(2);
    }

    @Test
    void 역할은_여러_개를_가질_수_있다() {
        Center center = centerRepository.save(new Center("그린코트"));
        Membership 원장 = new Membership(center, "김대표", "01011112222");
        원장.addRole(Role.ADMIN);
        원장.addRole(Role.COACH);

        Membership saved = membershipRepository.save(원장);

        assertThat(saved.hasRole(Role.ADMIN)).isTrue();
        assertThat(saved.hasRole(Role.COACH)).isTrue();
        assertThat(saved.hasRole(Role.MEMBER)).isFalse();
    }

    @Test
    void 다른_센터의_멤버십은_조회되지_않는다() {
        Center a센터 = centerRepository.save(new Center("A테니스"));
        Center b센터 = centerRepository.save(new Center("B테니스"));
        Membership a회원 = membershipRepository.save(new Membership(a센터, "김혜원", "01033334444"));

        assertThat(membershipRepository.findByIdAndCenterId(a회원.getId(), b센터.getId()))
                .isEmpty();
    }
}
```

**배울 개념**
- 인증(Authentication)과 인가(Authorization)의 차이
- **왜 비밀번호가 없는가** — 기획서 9장. OTP가 유일한 인증 수단
- Spring Security 기본 동작 — 아무 설정 없으면 모든 요청이 401이 된다
- 불투명 토큰 vs JWT. 지금은 불투명 토큰으로 간다 (W5에 JWT로 교체)

- [ ] **Step 1: Security를 열어두는 설정**

`SecurityConfig`를 만들어 `csrf` · `formLogin` · `httpBasic`을 끄고 `anyRequest().permitAll()`로 둔다.
인증은 다음 태스크의 인터셉터가 담당한다.

검증:
```bash
./gradlew bootRun
curl -i http://localhost:8080/api/auth/otp/request -X POST \
  -H 'Content-Type: application/json' -d '{"phone":"01011112222"}'
```
기대: 401이 아니라 404 또는 200. **401이 사라지는 것**이 이 스텝의 목표다.

- [ ] **Step 2: OTP 발송 (콘솔 mock)**

`OtpService`는 문자를 실제로 보내지 않는다. 개발 단계에선 **콘솔에 출력**한다.
- 고정 코드 `123456`, TTL 5분
- 번호별로 발급 기록을 들고 있다가 검증 시 소모

기획서 9장의 방어 항목(재전송 rate limit, 일일 상한)은 이번 슬라이스 범위 밖이다. 주석 없이 넘어간다.

- [ ] **Step 3: 로그인 흐름 구현**

`AuthService.verifyOtp(phone, code)`가 해야 하는 일 — 기획서 3.2를 그대로 옮긴다.

```
1. OTP 검증
2. loginPhone == phone 인 Account 조회, 없으면 생성
3. contactPhone == phone 이고 status == PENDING 인 Membership이 있으면 → 그 계정에 연결하고 활성화
4. 이 계정의 멤버십 목록 조회
   - 0개 → 에러 "소속된 센터가 없습니다"
   - 1개 → 액세스 토큰 즉시 발급
```

## Task 11: Nginx 리버스 프록시와 TLS

**파일**
- 생성: `deploy/nginx.conf`

**인터페이스**
- 생산: `https://www.fortyall.net` 이 EC2의 8080으로 프록시된다

**배울 개념**
- 리버스 프록시가 무엇이고 왜 앞에 두는가
- TLS 종료(termination)가 어디서 일어나는가
- `X-Forwarded-For` — 프록시를 거치면 클라이언트 IP가 어떻게 되는가
- Let's Encrypt와 certbot 자동 갱신

- [ ] **Step 1: Route 53 A 레코드 생성**

호스팅 영역 `fortyall.net`에 레코드 추가.
- `www.fortyall.net` → A 레코드 → EC2 퍼블릭 IP (또는 Elastic IP)
- `fortyall.net` → `www`로 리다이렉트

**Elastic IP를 붙이는 것을 권한다.** 안 붙이면 EC2를 재시작할 때마다 IP가 바뀌어 DNS를 다시 고쳐야 한다.

검증:
```bash
dig +short A www.fortyall.net
```
기대: EC2 IP가 나온다 (전파에 몇 분 걸릴 수 있다)

- [ ] **Step 2: Nginx 설치와 설정**

EC2에 nginx를 설치하고 `www.fortyall.net`으로 온 요청을 `localhost:8080`으로 넘긴다.
`X-Forwarded-For`와 `X-Forwarded-Proto` 헤더를 반드시 전달한다.

- [ ] **Step 3: HTTPS 인증서 발급**

certbot으로 Let's Encrypt 인증서를 발급하고 자동 갱신을 등록한다.

- [ ] **Step 4: 검증**

```bash
curl -I https://www.fortyall.net
curl -I http://fortyall.net
```
기대: 첫 번째는 200 또는 404(경로 없음), 두 번째는 `301` 리다이렉트

- [ ] **Step 5: 갱신 리허설**

```bash
sudo certbot renew --dry-run
```
기대: 성공. **이걸 안 하면 90일 뒤 인증서가 만료되어 서비스가 죽는다.**

- [ ] **Step 6: 커밋 (직접 실행)**

```bash
git add deploy/nginx.conf
git commit -m "chore: Nginx 리버스 프록시와 TLS 설정"
```
