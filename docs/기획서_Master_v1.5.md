## 1. 문제 정의

### 1.1 현재의 운영 방식
소규모 테니스 레슨장 대부분은 **카카오톡 + 엑셀 + 수기 장부 + 전화**의 조합으로 운영된다.
그 결과 다음 문제가 반복된다.

- 회원의 잔여 회차를 즉시 확인할 수 없고, **재등록 시점을 놓친다**
- 결번·노쇼 기록이 사람 기억에 의존한다
- 코치와 인포 간 일정 공유가 어렵다
- 회원은 빈 시간을 직접 확인할 수 없어 모든 문의가 전화로 몰린다
- 매주 자동으로 반복되는 고정 레슨과 일회성 보강 예약을 함께 관리할 도구가 없다

### 1.2 해결하려는 문제 (가치 제안)
> **고정 레슨 운영에서 발생하는 일정 · 수업권 · 출석 · 재등록을 하나의 흐름으로 연결한다.**

- 회원: 내 잔여·다음 레슨을 스스로 확인하고, 빈 시간에 직접 예약한다
- 코치: 내 주간표가 자동으로 채워지고, 출석 한 번으로 회차가 정리된다
- 원장: 처리할 일이 한곳에 모이고, 재등록 안내가 자동으로 나간다

### 1.3 기술 포지셔닝
단순 "테니스장 관리 사이트"가 아니라 —
> **정기 스케줄과 횟수권이라는 서로 다른 생명주기를 정합성 있게 관리하는 멀티테넌트 예약 SaaS.**

핵심 기술 문제: ① 멀티테넌트 데이터 격리 ② 정기 스케줄 Materialization ③ 예약 동시성 제어
④ 수업권 Ledger 정합성 ⑤ 출석 상태 머신 ⑥ 충전 유예와 슬롯 생명주기 ⑦ API 멱등성 (→ 12장)

## 2. 서비스 개요

| 항목 | 내용 |
|---|---|
| 형태 | **멀티테넌트 SaaS** — 테니스장(센터)마다 셀프 가입, 센터별 데이터 완전 분리 |
| 플랫폼 | 웹 + **PWA** (설치 시 웹푸시 알림) |
| 결제 | 온라인 결제 없음 — 계좌이체·현장결제 + 관리자 승인 방식 |
| 과금 | **운영자(센터) 과금 구조 확정** — 무료 시작 → 유료 전환 (가격·시점 보류) |
| 인증 | 전 역할 공통 **휴대폰번호 + SMS OTP** (비밀번호·소셜 없음) |

### 관통 원칙
> **"센터마다 다른 것은 전부 설정(config)으로 뺀다."**
> 영업시간, 예약 간격, 상품 구성, 취소·노쇼·홀드·유예 정책, 셀프 변경 허용 범위, 알림 채널까지 —
> 코드에 하드코딩하지 않고 센터 관리자가 조립한다. 이것이 "범용"을 가능하게 하는 단 하나의 원칙이다.

### 부가 원칙
- **시스템은 기록하고, 판단은 사람이 한다** — 양도·환불·노쇼 복구 등 애매한 예외는 자동화하지 않고 관리자 재량 처리(모든 처리는 기록으로 남김).
- **판단 요소가 없는 승인은 만들지 않는다** — 빈 시간으로의 단순 이동처럼 시스템이 이미 아는 사실을 사람이 도장 찍게 하지 않는다.

## 3. 사용자 정의

### 3.1 페르소나

|---|---|---|
| 김대표 | 원장 겸 코치 | 소규모 센터 "그린코트" 운영, 직원 없음 — 관리자·코치 겸직 |
| 김혜원 | 신규 정기 회원 | 목 10:00 주 1회, 앱 적극 사용 |
| 김서연 | 기존 정기 회원 | 화 20:00, 3개월째. 가끔 야근으로 결번 |
| 최유나 | 회차제 회원 | 쿠폰 5회권, 스케줄 불규칙 — 매번 빈 시간 셀프 예약 |
| 김상진·김아들 | 2인 레슨 부자 | 토 11:00 한 슬롯 공유, 각자 계정·수업권 |
| 오할머니 | 오프라인 회원 | 앱 미사용 — 관리자·코치가 대신 관리 |
| 한코치 | 고용 코치 | 센터 확장 후 합류, 일부 권한 부여받음 |
| 윤다리 | 다중 센터 회원 | A센터 정기 + B센터 회차제, 계정(번호)은 하나 — 멀티테넌트 격리 검증용 |

### 3.2 계정 구조 — 계정 ↔ 멤버십 분리
**계정 = 사람(로그인 번호 1개), 멤버십 = 센터별 소속.** 계정 1 : 멤버십 N.

- 같은 사람이 A센터의 관리자이면서 B센터의 회원일 수 있다.
- 로그인은 계정 단위. 소속이 여럿이면 **센터 선택 화면**(하나면 바로 진입).
- 데이터 격리는 멤버십 단위 — 다른 센터 정보는 보이지 않는다.

**로그인 번호 ↔ 센터 연락처 분리:**
- 로그인 번호(계정): **본인만 변경** — 기존 번호 + 새 번호 이중 인증.
- 센터 연락처(멤버십): 해당 센터 관리자가 수정(알림 발송용).
- 예외: **활성화 전 = 멤버십과 본인 계정의 연결이 아직 완료되지 않은 상태**(계정이 "없는" 게 아님 — 타 센터에 이미 있을 수 있음). 이 상태에서만 관리자가 번호 수정·초대 재발송 가능. **첫 인증 시 동일 번호 계정이 존재하면 그 계정에 멤버십을 연결하고, 없으면 새 계정을 생성**한다. 이후 로그인 번호는 본인 전용.
- 목적: A센터 관리자의 수정이 B센터 로그인까지 바꾸는 **테넌트 경계 침범 방지**.

### 3.3 역할(Role)과 권한(Permission)
한 멤버십은 **Role을 복수로** 가질 수 있다(소규모 원장 = ADMIN + COACH).

- Role: `ADMIN / COACH / MEMBER` — 큰 구분
- Permission: 회원 생성 · 결제 승인 · 고정 변경 승인 등 — **관리자가 코치별로 부여**하는 세부 권한

| 기능 | 회원 | 코치(기본) | 코치(권한 부여 시) | 관리자 |
|---|:--:|:--:|:--:|:--:|
| 회원 생성·초대 | ✕ | ✕ | ○ | ○ |
| 결제 승인(충전) | ✕ | ✕ | ○ | ○ |
| 출석 처리 | 본인 QR | ○(수동) | ○ | ○ |
| 고정 변경 승인 | 요청 | ✕ | ○ | ○ |
| 휴강 등록 | ✕ | 신청→승인 | 신청→승인 | ○ |
| 실력 등급(NTRP) 조회·기록 | ✕ (본인도 불가) | ✕ | ○ (담당 회원) | ○ |
| 상품·설정 관리 | ✕ | ✕ | ✕ | ○ |
| 스케줄 조회 | 본인 | 본인 담당 | 본인 담당 | 전체 |

- 권한으로 수행한 모든 처리는 **처리 주체가 기록**(감사 로그)되고 관련자 알림에 표시된다.
- 코치 비활성(퇴사): 부여 권한 자동 소멸 + 담당 회원 **일괄 이관** — 이관 대상 코치와의 **슬롯 충돌 목록**을 표시하고 관리자가 개별 조정(자동 해결 없음). **미이관 고정 스케줄·미래 레슨이 남아 있으면 비활성 완료 불가**(고아 레슨 방지 — 이관 후 비활성).
- 셀프 가입 남용 방어: rate limit + "회원 0명·장기 미접속 센터" 자동 정리.

### 3.4 역할별 정의
- **플랫폼 운영자(우리)** — 지원·모니터링·해지 처리, 플랫폼 고객센터. 센터 생성은 셀프 가입이 기본(수동 생성은 영업 예외).
- **관리자(사장님/인포)** — 셀프 가입으로 센터를 만든 본인 또는 초대된 직원. 회원·결제·스케줄·설정·통계.
- **코치** — 자기 스케줄, 담당 회원·레슨 노트, 출석 처리, 휴강 신청, 슬롯 닫기.
- **회원** — 수업권·레슨 조회, 예약·변경, 출석. **오프라인 회원**(앱 미사용)도 완전 지원.

## 4. 핵심 도메인 모델 — "수업권 + 고정 스케줄"

시스템의 심장. 두 개념으로 모든 이용 형태(정기·회차제·1인·2인·체험)를 표현한다.

### 4.1 수업권 (LessonPass)
회원이 보유한 레슨 이용 권리. **모든 수업권은 횟수권**(기간 내 무제한 없음).
한 회원이 수업권을 여러 개 보유할 수 있다(예: 20분 10회권 + 체험 1회권).

**횟수의 세 가지 상태 — 잔여 / 확보(예약됨) / 사용 완료:**
- **셀프 일회 예약 = 1회 확보** → 출석 시 사용 완료, 정상 취소 시 확보 해제.
  **추가 예약 가능 횟수 = 잔여 − 확보** — 잔여보다 많은 예약을 잡을 수 없다.
- **고정 스케줄 레슨은 확보하지 않는다** — 매주 자동 생성되고 출석 시점에 차감.
  잔여가 부족해도 레슨은 생성되며 충전 유예·외상이 이를 받는다(→ 6.3).
  이 비대칭이 유예 구조와 정합을 이루는 핵심이다.

**차감 규칙:**
- 출석 = −1
- 정당한 결번(사전취소·휴강) = 차감 없음 — **회차가 수업권에 남는 것이 결번 처리의 전부**
- **노쇼·늦은 취소 = 예외적으로 차감(기본)** — 단, 회원↔관리자 커뮤니케이션으로 관리자가 **회차 복구** 가능

**수명 관리:**
- **결제 확인**: 입금/현장결제 확인 → 관리자 승인(+받은 금액 기록) → **첫 구매·재등록이면 새 Pass 발급**, 기존 Pass의 예외 보정이면 조정/복구 트랜잭션. UI에서는 "충전"으로 표현 가능
- **Pass 생명주기 (정합성 규칙)**:
  - 상태: `대기(선결제) → 활성 → 소진 / 만료 / 취소`. **소진·만료 Pass는 '재등록'으로는 재활성화하지 않는다**(재등록 = 항상 새 Pass 발급). 단, **잘못된 차감 복구·관리자 조정·유효기간 연장처럼 기존 계약을 바로잡는 행위는 조건부 ACTIVE 복귀를 허용** — 소진 Pass에 복구로 잔여>0이 되고 유효기간 내이면 활성으로, 만료 Pass에 연장으로 새 만료일이 유효하고 잔여>0이면 활성으로(상태와 잔액의 모순 방지).
  - **만료-연장의 Ledger 정합**: 만료 시 잔여 소멸은 `만료 차감 −N` 트랜잭션으로 기록 → 관리자 연장은 날짜 변경 + **`만료 복구 +N` 트랜잭션**을 함께 수행(그래야 잔여>0 복귀 조건이 성립하고 "왜 3회가 돌아왔나"에 장부가 답함).
  - **유효기간 단축 조정 시 재검증**: 새 만료일 이후에 확보된 셀프 예약이 있으면 자동 반영하지 않고 **충돌 예약 목록을 표시 → 관리자가 취소/Pass 변경/만료일 재조정 결정**("판단은 사람").
  - **Grace 중 외상의 기록 대상**: 직전 Pass의 Ledger에 외상 출석 트랜잭션으로 기록(소진·만료 상태여도 허용, 단 상태는 활성으로 바꾸지 않음) → 새 Pass 발급 시 Carry-over 상계.
  - **구매일과 사용 시작일(validFrom) 분리** — 신규는 validFrom=결제 승인일, **선결제 Pass는 '대기' 상태로 두고 실제 승계 시점부터 유효기간 기산**(관리자 조정 가능). 대기 상태에선 예약·차감 불가.
  - **외상 Carry-over 정산**: 새 Pass 발급 시 이전 외상을 먼저 정산 — 옛 Pass에 `외상 정산 +N`으로 잔액 0 마감, 새 Pass에 `이월 외상 −N` 기록. UI: "10회 재등록 완료, 이전 외상 2회 정산 — 사용 가능 8회".
  - 용어: UI는 "충전/재등록"으로 표현하되, 도메인 행위는 **발급/조정/복구** — Pass에 '재충전'이라는 행위는 없다.
- 유효기간: 상품에 정의. 기산일 = 결제 승인일 기본(관리자 조정 가능). 만료 시 잔여 기본 소멸, 관리자 연장 가능(부상 등 예외 흡수)
- **모든 횟수 변동은 트랜잭션으로 기록**(구매/출석/노쇼/복구/조정/만료) — "왜 지금 7회인가"에 답한다. 관리자 임의 수정도 조정 트랜잭션(→ 12장 Ledger)
- 수업권이 여러 개일 때 차감 대상은 **예약 시점에 결정**: 고정 레슨은 연결된 수업권 자동, 셀프 예약은 선택. 우선순위 자동 규칙 없음.

**재등록·승계·예약 범위 (운영 교차 규칙):**
- **재등록 = 새 LessonPass 발급.** UI에서는 "충전"으로 표현해도, 내부에서는 기존 Pass에 횟수를 더하지 않고 **새 Pass를 발급**한다(기존 Pass의 구매 시점 스냅샷과 새 판매 조건이 섞이지 않게).
- **선결제 승계**: 고정 스케줄에 연결된 Pass가 소진되면, **같은 스케줄용으로 선결제된 다음 Pass가 있으면 자동 승계**한다. ※ 이는 "우선순위 자동 규칙 없음" 원칙의 예외가 아니다 — 승계는 그 스케줄 전용으로 회원이 선결제한 Pass로 넘어가는 것이라 애매성이 없고, 셀프 예약의 선택권은 그대로다.
- **만료일 이후 레슨 예약 불가**: `레슨 시작 ≤ 수업권 만료일` 인 경우에만 그 수업권으로 예약 가능. **만료일은 센터 로컬 타임존 기준 그 날짜의 종료 시점(end-of-day)까지 유효** — 8/31 만료면 8/31 저녁 레슨도 사용 가능. MVP는 Asia/Seoul 고정, 향후 센터별 타임존 확장.
- **정기 회원의 셀프 예약 경고**: 잔여를 셀프 예약에 자유롭게 쓸 수 있되, 미래 고정 레슨 수보다 잔여가 부족해질 예약에는 경고를 표시 — "예정된 고정 레슨 3회가 있습니다. 이 예약 시 재등록이 필요할 수 있습니다." (막지 않음 — 유예·외상이 받는다)

### 4.2 고정 스케줄 (Standing Schedule)
"매주 화 20:00 · 김코치 · 20분" — **규칙 하나가 매주 레슨을 자동 생성**한다.

- 정기 회원 = 수업권 + 고정 스케줄 / 회차제 회원 = 수업권만
- 주 2회 = 규칙 2개(화 19:00 + 목 19:00) — **여러 고정 스케줄이 하나의 수업권을 공유**한다(Pass:스케줄은 1:1이 아님). **선결제 승계도 스케줄 하나가 아니라 그 회원의 정기 이용 관계 전체 단위**로 적용(화요일에 소진되면 목요일부터 새 Pass). **회원별 정기 이용 생명주기는 "정기 등록(RegularEnrollment)" 개념으로 관리한다(확정)** — 회원 1명의 정기 이용 관계(현재 Pass·다음 Pass·Grace·홀드·상태)를 담는 단위. 여러 고정 스케줄(주 2회)이 하나의 정기 등록에 묶이고, 2인 레슨은 한 스케줄에 정기 등록 2개가 참가한다. **홀드·Renewal Grace는 스케줄이 아니라 이 단위의 상태** — 그래야 "김상진만 홀드, 김아들은 계속"이 표현된다. 스케줄 자체는 시간·슬롯 규칙의 생명주기(활성/종료)만 가진다.
- 저장 전략 = **materialize**: 미래 레슨 레코드를 미리 생성(레슨마다 출석·차감·변경 상태가 붙으므로). **생성 범위(Horizon)는 매일 rolling으로 90일 유지 — 항상 최대 Booking Window(60일) 이상**이어야 함. 그래야 회원이 조회하는 모든 예약 범위에 정기 레슨이 이미 존재해, 미생성 정기 슬롯을 빈 시간으로 오인하는 이중 예약이 원천 차단된다.
- **고정 변경은 적용 시작일(effectiveFrom) 기준** — 이전 레슨 유지, 이후 자동생성분 재생성. **회원이 개별 이동한 레슨은 재생성이 덮어쓰지 않는다**
- 회원 중단 시 **해당 스케줄 참가자를 해제**한다. **활성 참가자가 0명이 된 경우에만 고정 스케줄을 종료**하고 슬롯을 빈 시간으로 전환(→ 4.3과 동일 규칙)

### 4.3 레슨 상품 (Product)
차이를 코드가 아니라 데이터로 흡수한다.

- 속성: `길이`(20/30/60분…) · `인원`(1인/2인) · `가격` · `횟수` · `유효기간` · `설명`(환불 규정 등 자유 기재)
- **구매 시 조건 스냅샷** — 상품을 나중에 수정해도 이미 판매된 수업권의 조건은 불변
- **1인/2인 = 함께 오는 일행 수** (부자·커플). 같은 슬롯 공유, **각자 회원 · 각자 수업권 · 각자 QR · 각자 출석 상태**. 슬롯 점유는 1건, 요금만 1인가/2인가(가격은 **회원 1인 기준**). 오픈 그룹(모르는 사람 합류) 없음. **중단은 참가자 단위로 해제하며, 활성 참가자가 0명이 될 때 고정 스케줄이 종료되고 슬롯이 빈칸이 된다**(한 명 남으면 유지 — 1인 회원의 중단은 참가자 1명 해제 = 즉시 종료로 같은 규칙의 특수 케이스). **2인→1인 전환은 기존 Pass 스냅샷을 수정하지 않고 다음 구매부터 1인 상품으로 발급**(그 사이 금액 정산만 인포 재량)
- **1회권 포함 임의 횟수 지원** — 체험레슨 = 횟수 1 상품. 특별 취급 없음

### 4.4 슬롯 & 빈 시간 — 시간 구간 모델
- **예약 시작 간격(booking interval)** 과 **레슨 길이(duration)** 를 분리한다.
  예: 간격 10분 + 30분 상품 → 19:00~19:30, 19:10~19:40 …
- 레슨은 `시작~종료` 구간으로 관리, 예약 가능 판정은 **시간 구간 겹침(overlap) 검사** — 같은 코치의 기존 레슨과 구간이 겹치면 불가. 동시 요청은 한 명만 성공(→ 12장 동시성)
- **슬롯 상태 = 확정 또는 빈칸** (임시 점유 없음) — 모든 등록·충전이 관리자 승인 경유라 "돈 안 낸 유령 슬롯"이 구조적으로 발생하지 않는다
- 빈 시간 = 코치 근무시간 − (고정 스케줄 + 셀프 예약 + 닫은 구간)
- **사전취소·이동으로 비워진 정기 슬롯은 그 주에 한해 빈칸** — 다른 회원이 예약 가능
- **슬롯 열기/닫기**: 관리자·코치가 근무시간(요일 반복/특정일)을 등록해 빈 시간을 만들고, 개인 사정 구간은 닫기로 막는다(휴강과 다름 — 닫기는 예약 전 시간을 막는 것)
- 수업권 보유자의 셀프 예약은 **즉시 확정** — 확인 모달: "수업권 1회가 예약(확보)됩니다"
- **Booking Window**: 셀프 예약 가능 범위는 오늘 기준 **기본 30일**(센터 설정: 7/14/30/60일) — 인기 시간 장기 선점 방지.
- **보강 셀프 예약의 코치 범위: 기본 담당 코치만**(진도·스타일 유지) — 센터 설정으로 "모든 코치 허용" 전환 가능.

### 4.5 출석 — 상태 5종
QR은 "있으면 좋은" 접점, **신뢰 경로는 코치 수동 처리**.

- **QR 방식: 회원 앱이 QR 제시 → 코치가 스캔.** 출석 가능 시간 제한 없음(자기 회차 차감이라 부정 동기 없음, 오차감은 확인 모달로 방지)
- 단 **QR 토큰은 짧은 만료의 서명 토큰**(보안) — "출석 시간 무제한 ≠ QR 영구 유효". 스캔 시 서버가 멤버십·코치 권한·대상 레슨·중복 여부 검증
- 스캔 순간 **코치 화면에 회차·잔여 표시**("오늘 3/5회, 잔여 2") → 갱신 대화가 코치 쪽에서 자연 발생
- 회원 폰 부재·오프라인 회원 → 코치 수동 출석

| 상태 | 정의 | 차감 |
|---|---|---|
| 출석 | 정상 수업 | −1 |
| 사전취소 | 규정 시간 내 연락 | 없음 |
| 늦은 취소 | 연락했으나 규정 초과 | 정책(기본 차감·복구 가능) |
| 노쇼 | 연락 없이 불참 | 정책(기본 차감·복구 가능) |
| 휴강 | 코치·센터 사유 | 없음 |

- 늦은 취소와 노쇼는 차감이 같아도 **의미를 분리 집계** — "노쇼 5회"와 "노쇼 1 + 늦은 취소 4"는 회원 판단이 다르다
- **미처리 레슨**(종료 후 아무 상태 없음) → 관리자 처리 큐에 노출, 사후 지정. **자동 노쇼 없음**(판단은 사람)

### 4.6 실력 등급 (NTRP) — 관리자 전용 내부 정보
회원의 테니스 실력을 **NTRP 등급(1.0~7.0, 0.5 단위)** 으로 기록·관리한다.

- **회원은 입력할 수 없고 볼 수도 없다.** 기본 접근 = 관리자 전용. 코치는 **권한 부여(Permission)** 로 담당 회원에 한해 조회·기록 가능(센터 선택).
- **평가 이력으로 기록** — 등급·평가일·평가자를 남긴다(단일 숫자 덮어쓰기 아님). 실력 변화 추이 확인 가능. 자유 메모 병기.
- **용도**: 자체 대회 조 편성·그룹 구성 시 비슷한 실력끼리 묶기 위한 **관리자 참고 데이터**. 회원 목록에서 NTRP 필터·정렬 지원. (매칭·대회 '기능' 자체는 스코프 아웃 유지 — 데이터만 제공)
- 관리자 화면에 **NTRP 기준 가이드**(1.0 입문 ~ 5.0+ 선수급, 수준별 설명) 를 참고로 제공해 평가 일관성을 돕는다.

### 4.7 개인정보 · 약관 · 탈퇴 — 이원화
- **센터 탈퇴**: 해당 멤버십만 종료(타 센터 소속 유지). 잔여 회차 있으면 **"잔여 N회 소멸" 경고 필수**, 환불은 인포 재량 안내
- **플랫폼 계정 탈퇴**: 계정 삭제. 활성 멤버십·미사용 수업권·관리자/코치 역할 존재를 검증 후 진행. 개인정보 파기(결제 기록은 법정 기간 보관 후 파기)
- 활성화 시 약관·개인정보 동의. 탈퇴 ≠ 휴면(휴면은 복귀 가능한 상태)
- **내부 평가 정보**(NTRP·레슨 노트·회원 메모)는 회원 비공개 운영 정보로 개인정보처리방침에 명시. 탈퇴 시 함께 파기.
- **센터 해지 시 소속 회원 전원 일괄 안내 문자** 후 비활성화

## 5. 사용자 여정 (요약)

상세 시나리오는 별도 문서(전 구간 시나리오 v6검증) 참조. 핵심 여정만 요약한다.

**J1. 센터의 탄생** — 김대표 셀프 가입 → 센터 자동 생성 → 세팅 체크리스트 → CSV로 기존 회원 12명 일괄 등록·초대

**J2. 회원의 시작** — 방문·상담 → 관리자가 생성+수업권 충전 → 현장 QR로 즉시 활성화 → 다음 주부터 자동으로 레슨이 잡혀 있음. (오할머니는 활성화 없이도 동일하게 관리)

**J3. 평범한 매주** — 전날 리마인더 → QR 제시·코치 스캔 → −1 → "오늘 2/4회차". 회원이 매주 뭔가 신청할 일이 없다.

**J4. 빠지는 주** — 하루 전 앱에서 취소 → 안 깎임 → 남은 회차는 다음 주가 자동 소비하거나 빈 시간에 셀프 보강. 대회는 관리자 일괄 취소, 공휴일은 휴강일 지정.

**J5. 재등록의 순간** — 잔여 1회 알림 → 마지막 출석 → 유예 7일(알림 3단계 + 인포 전화) → 입금·승인 = **새 수업권 발급, 기존 스케줄에 다음 Pass로 연결(소진 시 자동 승계)** — UI 표시는 "재등록 완료", 슬롯 그대로 / 무응답 = 자동 해제.

**J6. 예외들** — 6주 출장 = 홀드(만료일 자동 연장, 슬롯 잠금·관리자 수동 개방 가능) / 이번 주만 이동 = 즉시 / 요일 자체 변경 = 승인 / 노쇼 = 차감 후 대화로 복구 가능.

**J7. 끝** — 명시적 중단 = 즉시 해제 / 말없는 잠수 = 유예 후 자동 해제 / 노쇼 반복 = 휴면 / 센터 탈퇴·플랫폼 탈퇴 이원화.

## 6. 운영 플로우 상세

### 6.1 센터 온보딩 — 셀프 가입
1. 원장/강사 셀프 가입(번호+OTP) → 센터명 입력 → 센터 자동 생성, 본인 = 첫 관리자 (무료 시작)
2. 초기 세팅 체크리스트(건너뛰기 가능·진행률·홈 고정): ① 영업시간·예약 간격 ② 상품·요금 ③ 계좌 ④ 정책(기본값 제공) ⑤ 코치 등록
3. **CSV 일괄 등록**: 업로드 → 검증 → **프리뷰**(행 단위 오류: 번호 중복·상품 매칭 실패·슬롯 충돌) → 확정 → 성공/실패 리포트
   - 권장 필드: 이름·번호·담당 코치·고정 요일·시간·상품·**현재 잔여 횟수·현재 유효기간**
   - **기존 회원의 잔여는 `이관 개시 잔액(MIGRATION_OPENING_BALANCE)` 트랜잭션으로 기록** — 신규 구매가 아니므로 **결제 승인 금액·판매 통계에서 제외**하고, 기존 만료일을 그대로 보존한다. 과거 출석 이력 전체 이관은 하지 않음(도입 시점 현재 상태만).
- 소규모: 가입자 = 관리자 = 코치(다중 Role). 플랫폼 수동 생성은 영업 예외.

### 6.2 회원 온보딩 — 관리자 생성
**회원의 계정 = 전화번호. 첫 로그인(번호+OTP)이 곧 활성화.** 비밀번호·아이디·별도 가입 없음.
1. 방문·상담 → 관리자가 생성(이름·번호) + 코치·고정 슬롯 배정 + 상품 선택 + 수업권 충전
2. **초대 다채널**: 문자 링크 + 현장 QR(그 자리 활성화) + 카톡 공유
3. 활성화(약관 동의) → 이미 레슨·수업권 세팅 완료 → PWA 설치 유도
- 결제 확인 ↔ 활성화 독립(순서 무관). 오프라인 회원 완전 지원.
- **오프라인 회원 개인정보 동의 기록**: 활성화하지 않아도 센터는 이름·번호·결제·NTRP 등을 저장하므로, **동의 확인 상태(확인 여부·일시·확인자)를 시스템에 기록**한다(현장 확인 → 관리자 체크). 법적 절차 상세는 정책 단계에서 확정하되 상태 기록은 필수.

### 6.3 갱신 · 충전 유예 · 외상
- 잔여 1회(설정) → **갱신 알림**(문자+푸시)
- **활성 Pass 부재(소진 또는 유효기간 만료) & 다음 Pass 없음 → Renewal Grace 시작(기본 7일)**: 슬롯 보장, 레슨 계속 생성("충전 필요" 표시). Ledger상 원인(잔여 소진 vs 기간 만료)은 다르지만 **슬롯 보호는 동일한 Grace 정책 하나로 통일** — 만료로 남은 잔여는 기존 정책대로 소멸(관리자 연장 가능), 다음 Pass가 선결제돼 있으면 Grace 없이 즉시 승계
  - 알림: 즉시 → 3일 후 → 만료 전날 최종 경고. 관리자 큐 "충전 대기" 표시
  - 유예 내 충전 → 계속 / 만료 무응답 → 자동 해제 → 빈칸(재등록 시 비어있으면 복귀)
- **외상(기본 허용)**: 유예 중 레슨이 먼저 오면 진행 + 잔여 −1 기록. 노쇼 겹치면 −2 가능. **새 Pass 발급 시 Carry-over로 정산**(옛 Pass 0 마감 + 새 Pass에 이월 외상 차감 → 4.1)
- **유예 = 정기(고정 스케줄) 전용** — 슬롯 보호 장치. 회차제는 재구매로 충분
- **유예(잔여 0) ≠ 유효기간 만료(잔여 있음)** — 별개 트랙: 전자 슬롯 보호, 후자 잔여 소멸(연장 가능)

### 6.4 결번 · 일괄 처리
- 사전취소 규정 기본 24h(설정). 초과 취소 시도 시 **UI 경고 필수**("지금 취소하면 차감됩니다")
- 일부 결번(대회): 회원 개별 취소 or **관리자 일괄 사전취소**(명단 선택 → 일괄 처리+알림)
- 전원 결번(공휴일·점검): **휴강일 지정** → 해당일 전체 휴강 + 일괄 알림
  - **휴강일·코치 부재는 독립적인 일정 예외 데이터(Calendar Exception)로 저장 — 양방향 처리**: ① 이미 생성된 해당 날짜 레슨은 **즉시 휴강 처리 + 차감 없음 + 알림**, ② 아직 생성 전 날짜는 이후 Materializer가 Exception을 참조해 **생성 자체를 차단**. ③ **Exception 삭제(휴강 등록 실수) 시 휴강 처리된 레슨을 자동 복구하지 않는다** — 그 시간의 현재 예약·충돌을 재검증하고 관리자가 재개를 확정("판단은 사람").
- **정상 사전취소는 회차를 보존하지만 유효기간을 자동 연장하지 않는다** — 구매·취소 화면에 명시 고지(분쟁 예방). 부상·장기 사유만 관리자 연장.
- 코치 휴강: 신청 → 관리자 승인 → 담당 레슨 휴강 + 알림

### 6.5 예약 변경 — 이원화
| 종류 | 처리 | 근거 |
|---|---|---|
| 이번 주만 이동(빈 시간으로) | **회원 즉시 변경** + 관리자·코치 알림 | 판단 요소 없음 — 승인은 도장 노동 |
| 고정 요일·시간 자체 변경 | **관리자 승인** | 요금(평일/주말)·스케줄 구성에 영향 |
- 셀프 변경 고삐: 당일 불가·월 N회 제한(설정). 고정 변경 승인 시 **대상 시간 재검증** 후 effectiveFrom 기준 재생성.

### 6.6 홀드(일시정지)
- 관리자가 기간 설정, 최대 기본 6개월(설정)
- 홀드 중: 레슨 미생성 · 차감 없음 · **유효기간 정지 = 만료일이 실제 홀드 일수만큼 연장**(만료 8/31 + 홀드 20일 → 9/20)
- 슬롯 기본 잠금. 관리자 수동 개방 가능 — 개방분은 **홀드 기간 내 일회 예약만**(고정 배정 불가)
- **홀드 조기 종료(복귀 일정 변경) 시 재검증**: 단축 구간에 이미 확정된 일회 예약이 있으면 **충돌 목록을 표시하고 관리자가 수동 조정**(자동 취소 없음 — "판단은 사람" 원칙).
- **홀드는 활성 정기 등록에서만 시작 가능** — Renewal Grace 상태에서는 홀드 불가(슬롯 보호 기간을 우회 연장하는 것 방지). 예외는 관리자 강제 처리 + 감사 기록.
- **2인 레슨의 참가자별 홀드**: 한 명만 홀드 = 그 참가자의 레슨 생성만 제외, 다른 참가자 수업은 계속 → 슬롯은 점유 유지·수동 개방 불가. **모든 참가자가 홀드일 때만** 슬롯 잠금 + 관리자 수동 개방 가능(6.6의 기존 규칙은 이 경우에 적용).

### 6.7 노쇼·늦은 취소 관리
- 기본 차감이되 **커뮤니케이션으로 복구 가능한 차감**. 대시보드에서 건별: 복구/경고/유지
- 노쇼·늦은 취소 분리 집계. 누적: 1회 알림 → 2회 경고 문자 → 연속·연락두절 → **휴면 전환 제안**(슬롯 해제)

### 6.8 예외 처리
양도·환불 등 = 자동화하지 않음. 관리자가 수업권 **조정 트랜잭션**으로 재량 처리.

## 8. 알림 설계

| 채널 | 역할 | 비고 |
|---|---|---|
| PWA 웹푸시 | 일상 알림(리마인더·변경·상태) | 무료, 설치·허용자 한정 |
| 문자(SMS) | 중요 안내(갱신·유예·초대·OTP) | **공용 발신번호** — 센터 세팅 0 |
| 카카오 알림톡 | (향후) 원하는 센터만 자기 채널 연결 | 템플릿 심사 필요 |

- `NotificationChannel` 추상 레이어로 채널 교체 가능, 센터별 on/off
- **오프라인(미활성화) 회원 fallback**: 활성화 여부에 따라 채널 자동 선택 — 앱 회원은 푸시, 오프라인 회원은 **SMS로 대체 발송**(전날 리마인더 포함, 센터 설정으로 on/off).
- **회원 개인 알림 토글** — 단 갱신·결제 등 필수 안내는 끌 수 없음
- **알림함**(회원 인앱, 지난 알림 모아보기) + **발송 이력**(관리자, "문자 못 받았어요" 분쟁 대비)
- 갱신·출석·리마인더는 정보성 문자 — 광고 규제(수신동의·야간제한) 대상 아님

### 주요 알림 매트릭스
| 이벤트 | 대상 | 채널 |
|---|---|---|
| 레슨 전날 리마인더 | 회원 | 푸시 (오프라인 회원은 SMS, 설정) |
| 잔여 1회 / 유예 시작·3일·만료 전날 | 회원 | 문자+푸시 |
| 이번 주 이동(즉시 변경) | 관리자·코치 | 푸시 |
| 고정 변경 승인/거절 | 회원 | 문자+푸시 |
| 휴강·휴강일·일괄 취소 | 해당 회원 전원 | 문자+푸시 |
| 노쇼 기록/경고 | 회원 | 문자 |
| 초대·OTP | 대상자 | 문자 |
| 센터 해지 | 소속 회원 전원 | 문자 |

## 9. 인증 설계

- 전 역할 공통: **번호 + SMS OTP(6자리)**. 첫 인증 성공 = 활성화(회원) / 가입(운영자)
- "이 기기 기억하기"로 재인증 최소화
- **로그인 번호 변경 = 본인 전용**(기존+새 번호 이중 인증). 활성화 전 부트스트랩만 관리자 수정
- 방어: OTP 재전송 rate limit · 일일 발송 상한(비용) · 시도 횟수 제한

## 12. 설계 원칙 (구현 단계 가이드)

ERD·상태머신·트랜잭션 설계의 출발점.

1. **수업권 Ledger** — 잔여는 숫자 하나가 아니라 **트랜잭션의 합**(구매/출석/노쇼/복구/조정/만료). 관리자 수정도 조정 트랜잭션. Audit Log(누가 무슨 행위)와 Pass Transaction(잔액이 왜 변했나)은 목적이 달라 **병행 기록**.
2. **참가자 분리(레슨·스케줄 양쪽)** — 출석 상태는 레슨이 아니라 **참가자 단위**(2인: 아버지 출석·아들 노쇼), 수업권도 참가자별 독립 차감. 고정 스케줄도 **StandingScheduleParticipant(1:N)** 로 표현 — 이 구조 하나로 1인/2인/주2회(여러 스케줄이 Pass 공유)/한 명 중단/승계가 동일하게 표현된다. Pass:스케줄을 1:1로 만들지 말 것.
3. **상태 머신 명시** — 아래 13장 상태 모델을 설계 단계에서 전이표(상태→이벤트→다음 상태→부수효과)로 완성.
4. **Materializer 멱등성** — (고정 스케줄 ID + 발생 날짜) 유니크 제약. 수동 수정 레슨은 덮어쓰지 않음. 변경은 effectiveFrom 기준.
5. **동시성 5대 시나리오** — 같은 시간 동시 예약(한 명만) · QR 중복 스캔(1회만 차감) · 결제 승인 중복(**Pass 1개만 발급**) · Materializer 중복 실행(레슨 1개만) · **이번 주 이동 중 슬롯 경쟁**(신규 슬롯 확보 + 기존 레슨 변경을 **하나의 트랜잭션**으로 — 실패 시 롤백해 기존 자리 보존). Unique Constraint · Lock · Idempotency Key로 해결.
   - 2인 레슨의 **이번 주 이동은 참가자 전체 단위로만** 처리(한 명만 옮기면 2인 상품이 1인 레슨 2개로 분리됨). 개별 이동은 관리자 재량.
6. **책임 경계 4분할** — StandingSchedule = 시간·슬롯 규칙 / RegularEnrollment = 회원별 정기 생명주기(홀드·Grace·승계) / LessonPass = 이용 권리·잔액(Ledger) / Lesson = 실제 발생 수업(참가자별 출석). ERD 첫 검증 대상은 `정기 등록 ↔ 스케줄 참가자 ↔ 스케줄` 3자 구조.
7. **시간 구간 충돌** — 예약 판정은 `기존.시작 < 요청.종료 AND 기존.종료 > 요청.시작` overlap 검사.

## 13. 상태 모델 (초안)

설계 단계에서 전이표로 확장한다. 여기서는 상태값과 핵심 전이만 정의.

**레슨 참가자**: `예정 → 출석 / 사전취소 / 늦은취소 / 노쇼 / 휴강` (노쇼·늦은취소는 복구 이벤트로 차감 원복 가능, 상태는 유지·기록)

**수업권**: `대기(선결제) → 활성 → 소진(잔여 0) / 만료(유효기간) / 취소(관리자)` — **'재등록'에 의한 복귀 없음**(재등록 = 새 Pass 발급). 단 **복구·조정·유효기간 연장은 조건 충족 시(잔여>0 & 기간 내) 활성 복귀 허용**(상태-잔액 모순 방지). **Renewal Grace는 Pass 상태가 아니라 고정 스케줄/갱신 생명주기의 상태** — StandingSchedule에 직접 둘지 별도 생명주기 객체로 둘지는 ERD에서 결정.

**정기 등록(RegularEnrollment)**: `활성 ⇄ 홀드 / 활성 → Renewal Grace → 활성(재등록) 또는 종료 / 활성 → 종료(명시적 중단)` — 회원별 생명주기. **홀드·Grace는 여기에 산다.**

**고정 스케줄**: `활성 → 종료(활성 참가자 0명)` — 시간·슬롯 규칙 자체의 생명주기만. Grace 만료는 스케줄이 아니라 **해당 참가자(정기 등록)를 종료**시키고, 스케줄은 활성 참가자 수로만 종료가 결정된다.

**멤버십**: `미활성(부트스트랩) → 활성 ⇄ 휴면 / → 센터 탈퇴`

**계정**: `활성 → 플랫폼 탈퇴(검증 후)`

**센터**: `활성 → 정지 / 해지`

### 운영 시나리오 추가 결정 (v1.2)
"두 개의 정상 기능이 실제 운영에서 만났을 때"의 규칙 확정. 본문 해당 절에 반영 완료.

1. 기존 회원 이관 잔여 = **이관 개시 잔액** 트랜잭션 — 판매 통계 제외, 기존 만료일 보존 (→6.1)
2. 정기회원 셀프 예약 허용 + **미래 고정 레슨 대비 부족 경고** (→4.1)
3. **재등록 = 새 LessonPass 발급** (UI는 "충전", 스냅샷 혼합 방지) (→4.1)
4. **선결제 Pass 자동 승계** — 같은 고정 스케줄 전용, 우선순위 원칙과 무충돌 (→4.1)
5. 수업권 **만료일 이후 레슨 예약 불가** (→4.1)
6. **Booking Window 기본 30일** (→4.4, 7장)
7. 2인 레슨 **이번 주 이동 = 참가자 전체 단위** (개별은 관리자 재량) (→12장)
8. 2인 개별 취소 허용, 한 명 남으면 슬롯 유지 (기존 확정 재확인)
9. 상품 가격 = **회원 1인 기준** (→4.3 해석 기준)
10. 오프라인 회원 리마인더 **SMS fallback** (센터 설정, 기본 ON) (→8장)
11. **오프라인 회원 동의 확인 상태 기록** (→6.2)
12. 코치 비활성 전 **담당 스케줄 이관 완료 강제** (→3.3)
13. 휴강일·코치 부재 = **Calendar Exception 독립 저장**, Materializer 참조 (→6.4)
14. **홀드 조기 종료 시 개방 슬롯 예약과 재검증** — 충돌은 수동 조정 (→6.6)
15. 첫 활성화 시 **동일 번호 기존 계정에 멤버십 연결** (신규 생성 아님) (→3.2)
16. **이번 주 이동 = 단일 트랜잭션** (확보+변경 원자 처리, 동시성 5대로 확장) (→12장)
17. **운영 정책 변경 = 행위 시점의 현재 정책 적용** — 계약 조건(가격·횟수·유효기간)만 스냅샷, 변경 시 "즉시 전체 적용" 안내
18. 정상 사전취소는 회차 보존하되 **유효기간 자동 연장 없음** — 화면 고지 (→6.4)
19. 보강 셀프 예약 코치 범위 **기본 담당 코치만** (설정으로 전체 허용) (→4.4, 7장)
20. **윤다리(다중 센터 회원) 페르소나 추가** — 멀티테넌트 격리 검증용 (→3.1)
