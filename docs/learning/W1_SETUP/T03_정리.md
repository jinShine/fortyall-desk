## 3. 유니크 제약

### 단일 컬럼

```java
@Table(name = "accounts", uniqueConstraints = {
    @UniqueConstraint(name = "uk_accounts_email", columnNames = "email"),
    @UniqueConstraint(name = "uk_accounts_phone_number", columnNames = "phone_number")})
```

**의도**: 이메일과 전화번호는 **사람을 찾는 열쇠**다. 중복되면 로그인 시 누구인지 정할 수 없다.
- `email` — 관리자·직원 로그인의 신원
- `phone_number` — 회원 재로그인, 초대링크 연결 시 "이 번호로 계정이 이미 있나?" 판단

### 복합 컬럼 — 두 값을 붙여 하나의 열쇠로 본다

```java
@UniqueConstraint(name = "uk_center_memberships_center_phone",
                  columnNames = {"center_id", "contact_phone_number"})
```

위반 시 에러 메시지가 이렇게 나온다.

```
Duplicate entry '1-010-5555' for key 'uk_center_memberships_center_phone'
                 ↑ 두 값이 하이픈으로 붙어 하나의 값이 됐다
```

| 데이터 | 결과 |
|---|---|
| A센터(1) + 010-5555 | ✅ 윤다리 @ A센터 |
| B센터(2) + 010-5555 | ✅ 열쇠가 다르니 통과 |
| A센터(1) + 010-5555 (또) | ❌ 중복 |

**전화번호만 유니크로 걸면 윤다리가 B센터에 등록을 못 한다.** 조합이어야
"한 센터 안에서는 유일, 센터끼리는 무관"이 성립한다.

### `@Column(unique=true)` 를 쓰지 않는 이유

| | `@Column(unique=true)` | `@UniqueConstraint` |
|---|---|---|
| 제약 이름 | **못 정함** (난수) | **정할 수 있음** |
| 여러 컬럼 조합 | **불가** | 가능 |

이름이 중요한 이유 — **위반 시 에러 메시지에 그 이름이 찍히기 때문**이다.

```java
catch (DataIntegrityViolationException e) {
    if (e.getMessage().contains("uk_accounts_email"))        → "이미 가입된 이메일입니다"
    if (e.getMessage().contains("uk_accounts_phone_number")) → "이미 등록된 번호입니다"
}
```

이름이 `UK499j0u2xj3j5kb...` 면 어느 제약이 깨진 건지 코드로 구분할 수 없다.

### 왜 자바가 아니라 DB에 거나

```java
if (repository.findByEmail(email).isPresent()) throw ...;
repository.save(...);   // ← 이 사이에 다른 요청이 끼어들면 둘 다 통과
```

확인과 저장 사이에 틈이 있다. 그리고 배치·직접 SQL은 자바 검사를 안 지난다.
**DB 제약이 마지막 방어선이다.** 실무는 둘 다 쓴다 — 자바로 친절한 메시지, DB로 진짜 방어.

## 4. `@ManyToOne` — FK가 생기는 쪽

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "center_id")
private Center center;
```

### 읽는 법: "나 기준으로"

> `Many`(나, 소속이 여러 개) `To` `One`(센터 하나에)

**앞이 나, 뒤가 상대방.** 애노테이션을 쓴 클래스가 앞이다.
3교시의 "몇 개?를 양쪽에서 두 번 묻기"가 그대로 애노테이션 이름이 된다.

### 자바는 객체, DB는 숫자

```
자바:  private Center center;      ← 객체
  ↓ JPA 가 번역
DB:    center_id  bigint  MUL      ← 숫자 + 외래키
```

**DB에는 ERD에 그린 것과 똑같이 `center_id` 가 저장된다.** 달라지는 건 자바에서 다루는 모양뿐.

### 왜 `Long centerId` 가 아니라 객체인가

| | ID 방식 | 객체 방식 |
|---|---|---|
| 연관 조회 | 리포지토리로 다시 조회 | `m.getCenter().getName()` |
| 타입 안전 | ✕ `Long` 은 다 같아서 accountId 를 넣어도 컴파일 통과 | ✅ 컴파일러가 잡음 |
| 지연 로딩 | ✕ 직접 관리 | ✅ 프록시 |
| 함정 | 없음 | **N+1** |

JPA의 존재 이유가 이것 — **DB는 테이블과 FK로, 자바는 객체와 참조로 생각한다.
그 번역을 대신 해준다.**

### `nullable` 의 의미

```java
@ManyToOne(fetch = FetchType.LAZY)                      // account — nullable
@ManyToOne(fetch = FetchType.LAZY, optional = false)    // center  — 필수
```

`account` 가 null 일 수 있는 이유는 **오할머니**다. 원장이 등록했지만 초대링크를 안 눌렀으면
계정이 없다. 그래도 완전한 회원이다.

### `FetchType.LAZY` 를 반드시 명시하는 이유

`@ManyToOne` 의 **기본값은 EAGER** 다. 그대로 두면 소속을 조회할 때마다 센터를
안 쓸 때도 무조건 같이 가져온다.

`getCenter()` 가 주는 건 진짜 `Center` 가 아니라 Hibernate 가 상속해서 만든 **프록시(껍데기)** 다.
→ Task 2에서 기본 생성자를 `private` 아닌 **`protected`** 로 둔 이유가 이것. 상속하려면
부모 생성자에 접근할 수 있어야 한다.

## 5. `@OneToMany` — 만드는 조건 두 가지

`@OneToMany` 는 **DB에 아무 영향이 없다.** FK는 이미 `@ManyToOne` 쪽에 있다.
순전히 "자바에서 반대 방향으로도 걸어갈 수 있게 하는 편의"다.

그래서 질문은 **"그 편의가 값을 하느냐"** 다.

```java
@OneToMany(mappedBy = "centerMembership", cascade = CascadeType.ALL, orphanRemoval = true)
private List<MembershipRole> roles = new ArrayList<>();
```

| 코드 | 뜻 | 빼먹으면 |
|---|---|---|
| `mappedBy = "centerMembership"` | FK는 **저쪽 필드**가 관리한다 | JPA가 중간 테이블을 멋대로 만듦 |
| `cascade = CascadeType.ALL` | 부모를 저장하면 자식도 저장 | 자식을 따로 저장해야 함 |
| `orphanRemoval = true` | 리스트에서 빼면 DB에서도 삭제 | 리스트에서만 사라짐 |
| `= new ArrayList<>()` | 빈 리스트 초기화 | `addRole()` 에서 NPE |

`mappedBy` 의 값은 **상대 클래스의 필드 이름**과 같아야 한다.
`MembershipRole` 에 `private CenterMembership centerMembership;` 이므로 `"centerMembership"`.

### 만드는 조건

> ① **개수에 상한이 있다** ② **부모와 생사를 같이한다**
>
> 둘 다 만족하면 만들고, 하나라도 아니면 리포지토리로 조회한다.

| | 개수 | 만드나 |
|---|---|---|
| `CenterMembership` → 역할들 | 최대 3개 | ✅ |
| `Lesson` → 참가자들 | 1~2명 | ✅ |
| `Center` → 소속들 | 수백~수천 | ❌ |
| `LessonPass` → 원장 기록들 | 계속 쌓임 | ❌ |

`Center` 에 만들면 `center.getMemberships().size()` 한 줄이
`SELECT * FROM center_memberships WHERE center_id = 1` 을 실행한다.
**조건도 페이징도 못 건다.** 회원 800명이면 800행이 메모리로 올라온다.
리포지토리로 하면 `countByCenterId()` 로 1행이면 끝난다.

### 직접 확인한 동작

```
cascade = ALL         → 소속만 persist 했는데 역할 2개가 함께 저장됨
orphanRemoval = true  → 리스트에서 하나 빼니 DB에서도 삭제 (2 → 1)
```

`em.persist(김대표)` 한 줄로 `centers`·`center_memberships`·`membership_roles` 세 테이블에
데이터가 들어갔다.

## 6. 생성자 설계 — 두 종류의 사람이 한 테이블에

```java
private Account(String email, String passwordHash, String phoneNumber) { ... }

public static Account ofStaff(String email, String passwordHash) {   // 이메일 필수
    return new Account(email, passwordHash, null);
}
public static Account ofMember(String phoneNumber) {                 // 번호 필수
    return new Account(null, null, phoneNumber);
}
```

`accounts` 한 테이블에 **관리자(이메일 로그인)와 회원(번호 연결)** 이 함께 들어온다.
그래서 email · password_hash · phone_number 가 **전부 nullable** 이다.

그럼 "셋 다 null인 유령 계정"은 어떻게 막나 →
**생성자를 `private` 으로 잠그고 정적 팩토리 두 개만 열었다.**
`new Account(null, null, null)` 이 **컴파일 자체가 안 된다.**

Task 2의 *"객체는 항상 유효한 상태로 태어나야 한다"* 의 응용이다.

### package-private 생성자

```java
MembershipRole(CenterMembership centerMembership, Role role) { ... }   // 접근제어자 없음
```

같은 패키지에서만 호출 가능. `MembershipRole` 은 **혼자 만들어지면 안 되고**
반드시 `centerMembership.addRole()` 을 통해서만 생겨야 한다.
`public` 이면 리스트에 안 들어간 채로 객체만 만들어져 자바와 DB가 어긋난다.

## 7. 리포지토리 — 이름이 곧 쿼리

```java
Optional<Account> findByEmail(String email);
   → SELECT * FROM accounts WHERE email = ?
```

구현을 쓰지 않는다. **메서드 이름을 Spring Data가 파싱해서 쿼리를 만든다.**

| 이름 | 조건 |
|---|---|
| `findByEmail` | `where email = ?` |
| `findByIdAndCenterId` | `where id = ? and center_id = ?` |
| `findAllByCenterIdOrderByDisplayNameAsc` | `where center_id = ? order by display_name asc` |
| `countByCenterId` | `select count(*) ...` |

**필드명과 정확히 맞아야 한다.** `findByPhone` 이라고 쓰면 (필드는 `phoneNumber`):

```
No property 'phone' found for type 'Account'
→ 앱이 아예 안 뜬다
```

런타임이 아니라 **기동 시점에** 잡히는 게 다행이다.

### 반환 타입이 `Optional` 인 이유

없을 수 있는 조회는 `Optional` 로 감싼다. 그냥 `Account` 를 반환하면 없을 때 `null` 이 오고,
모르고 `.getId()` 를 부르면 NPE. **`Optional` 은 "없을 수도 있다"를 타입으로 강제한다.**

### 테넌트 격리는 리포지토리에서 강제한다

```java
Optional<CenterMembership> findByIdAndCenterId(Long id, Long centerId);
```

`findById` 가 아니다. **ID만으로 조회하면 다른 센터 회원도 가져와진다.**
앞으로 만들 모든 조회 메서드에 이 원칙이 적용된다.

## 8. N+1 — 직접 세어본 결과

윤다리가 센터 5곳에 소속된 상태에서 소속 목록을 조회하고 센터 이름을 읽었다.

```
[A] join fetch 없음  →  SELECT 6번   (소속 1 + 센터 5)
[B] join fetch 있음  →  SELECT 1번
```

### 쿼리가 언제 나갔나

```
SELECT 1  ← 소속 5건 조회
▸ "이제 센터 이름을 읽습니다"
SELECT 2~6 ← 여기서 5번이 더 나감
```

**조회할 때가 아니라 `m.getCenter().getName()` 을 부르는 순간** 나갔다.
`LAZY` 프록시가 실제 값에 접근할 때 DB로 가기 때문이다.

이름이 N+1인 이유: 목록 1번 + 항목마다 N번.

### `join` 과 `join fetch` 의 차이

| | 조인 | 결과에 담기 |
|---|---|---|
| `join` | ✅ (조건 걸 때) | ❌ 여전히 프록시 → **N+1 그대로** |
| `join fetch` | ✅ | ✅ 진짜 객체 |

`fetch` 라는 단어가 **"가져와서 담아라"** 를 뜻한다. 이게 빠지면
"조인했는데 왜 N+1이 나지?" 로 헤맨다.

### 그럼 항상 fetch 하면 되나 — 아니다

필요 없을 때 가져오면 낭비다. **판단 기준: 이 목록을 보여줄 때 연관 데이터를 항상 쓰는가?**

| 메서드 | 판단 |
|---|---|
| `findAllByAccountId` (센터 선택 화면) | 센터 **이름**을 항상 보여줌 → **fetch** ✅ |
| `findAllByCenterIdOrderByDisplayNameAsc` (회원 목록) | 이름·상태만 필요 → 불필요 |

### 함정 — 컬렉션 fetch + 페이징

`@OneToMany` 를 fetch 하면서 페이징하면 **SQL에 `limit` 이 안 붙는다.** 직접 확인했다.

```sql
select ... from center_memberships cm1_0
       join membership_roles r1_0 on cm1_0.id = r1_0.center_membership_id
                                                     ← limit 이 없다
```

3건만 원했는데 DB에서 20행(회원 10 × 역할 2)을 전부 가져와 **자바 메모리에서 잘랐다.**

**왜 `limit` 을 못 붙이나** — 조인하면 행이 뻥튀기돼서, `limit 3` 이
"회원 3명"이 아니라 "조인 결과 3행"을 의미하게 된다. 그러면 마지막 회원의 역할이 잘린다.

회원이 5천 명이면 1만 행을 메모리에 올리고 3건만 쓴다. **결과가 맞아서 더 위험하다** —
개발 중엔 데이터가 적어 못 느끼고 운영에서 터진다.

**해결**: `spring.jpa.properties.hibernate.default_batch_fetch_size: 100`
→ 프록시를 하나씩 조회하지 않고 `IN (id1, id2, ...)` 로 묶어 조회. 페이징도 정상 동작한다.
(W2 목록 화면에서 적용 예정)

## 10. 면접 질문

### Q1. 유니크 제약을 애플리케이션이 아니라 DB에 두신 이유는?

**의도** — 동시성을 고려해본 사람인지. 신입은 대개 `if (존재하면) throw` 로 끝낸다.

> 애플리케이션에서 조회 후 저장하면 그 사이에 다른 요청이 끼어들 수 있습니다. 두 요청이
> 동시에 '없음'을 보고 둘 다 저장하는 거죠. 배치나 직접 SQL처럼 애플리케이션을 안 지나는
> 경로도 있고요. 그래서 DB 제약을 최종 방어선으로 두고, 애플리케이션 검사는 사용자에게
> 친절한 메시지를 주는 용도로 씁니다.

**꼬리** — *"제약 위반 예외 처리는?"* → Spring이 `DataIntegrityViolationException` 으로 감싸준다.
제약 이름으로 어느 것이 깨졌는지 구분해 메시지를 만든다.

### Q2. 연관관계를 단방향/양방향 중 어떻게 정하셨나요?

**의도** — "양방향이 편하니 다 걸어두는" 사람인지. 실무 성능 문제의 흔한 원인.

> 컬렉션 크기에 상한이 있고 부모와 생명주기를 공유하면 양방향으로 뒀습니다. 소속-역할은
> 역할이 최대 3개고 소속이 지워지면 같이 지워져야 해서 `cascade` 와 `orphanRemoval` 을
> 걸었습니다. 반대로 센터-소속은 회원이 수백 명까지 늘 수 있어서 단방향으로 두고 리포지토리에서
> 페이징으로 조회합니다. `@OneToMany` 는 컬렉션을 통째로 로딩해서 조건이나 페이징을 걸 수 없거든요.

### Q3. N+1 문제가 뭔가요? 어떻게 발견하고 해결하셨나요?

**의도** — JPA 면접 단골 1순위. 써본 사람과 **겪어본** 사람을 가른다.

> 목록을 조회한 뒤 각 항목의 연관 엔티티에 접근하면 목록 1번 + 항목 수만큼 N번 쿼리가
> 나가는 문제입니다. 지연 로딩 프록시가 실제 값에 접근할 때 조회하기 때문입니다.
> `org.hibernate.SQL` 로그를 DEBUG로 켜서 발견했고, 소속 5건 조회에 SELECT가 6번 나가는 걸
> 확인했습니다. `join fetch` 로 바꾸니 1번으로 줄었습니다.

**꼬리 1** — *"`join` 과 `join fetch` 차이는?"* → `join` 은 조인만 하고 결과를 담지 않아
여전히 프록시. `fetch` 가 있어야 실제 엔티티를 가져온다.

**꼬리 2** — *"컬렉션 fetch join 에 페이징을 걸면?"* → 조인하면 행이 뻥튀기돼 `limit` 을 못 건다.
SQL 로그를 봤더니 `limit` 이 없고 전부 가져온 뒤 메모리에서 자르더라.
컬렉션은 `default_batch_fetch_size` 로 IN 절 묶음 조회를 쓰는 게 맞다.

**꼬리 3** — *"모든 연관관계를 EAGER로 하면?"* → 안 쓸 때도 항상 가져와 더 나쁘다.
그리고 EAGER여도 `findAll()` 같은 JPQL에서는 N+1이 그대로 난다.
**EAGER는 N+1의 해결책이 아니다.**

### Q4. 엔티티 생성자를 `private` 으로 두고 정적 팩토리를 쓰신 이유는?

> `accounts` 한 테이블에 관리자(이메일 로그인)와 회원(번호 연결) 두 종류가 들어와서
> 세 컬럼이 전부 nullable 입니다. 생성자를 열어두면 셋 다 null인 유령 계정이 생길 수 있어서,
> 생성자를 private 으로 잠그고 `ofStaff` · `ofMember` 두 개만 열었습니다. 잘못된 조합이
> 컴파일 자체가 안 됩니다.
