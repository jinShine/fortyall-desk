## 2. 핵심 개념 3개

### 2-1. 자동 구성 (Auto Configuration)

Spring Boot는 **클래스패스에 뭐가 있는지 보고 설정을 조건부로 켠다.**
(클래스패스 = 앱이 실행될 때 읽어들이는 라이브러리 목록. build.gradle 의존성들)

```
JPA 스타터가 있다 → "DB를 쓰겠구나" → DataSource 자동 생성 시도 → DB url 없음 → 실행 실패
```

| 애노테이션                  | 조건                                                   |
| --------------------------- | ------------------------------------------------------ |
| `@ConditionalOnClass`       | 특정 클래스가 있으면 자동 설정을 켠다                  |
| `@ConditionalOnMissingBean` | 같은 Bean을 내가 직접 만들지 않았을 때만 자동 생성한다 |

두 번째가 중요하다. **내가 직접 정의하면 자동 구성이 물러난다.** 나중에 SecurityConfig를
직접 만들면 기본 보안 설정이 비켜서는 이유가 이것이다.

### 2-2. Docker — 이미지 / 컨테이너 / 볼륨

|          | 무엇                                             | 컨테이너 삭제 시 |
| -------- | ------------------------------------------------ | ---------------- |
| 이미지   | 읽기 전용 템플릿 (설치 파일)                     | 안 지워짐        |
| 컨테이너 | 이미지를 실행한 것. 위에 **얇은 쓰기 층**이 얹힘 | **쓰기 층 삭제** |
| 볼륨     | 컨테이너 밖의 저장 디렉터리                      | 안 지워짐        |

```
┌─ 컨테이너 ──────────────────────┐
│  ┌ 쓰기 층 ────────────┐        │
│  │ /root/local.txt     │ ← 삭제됨
│  └─────────────────────┘        │
│  ┌ 이미지 층 (읽기전용) ┐        │
│  └─────────────────────┘        │
│    /var/lib/mysql ──┐ ← 구멍     │
└─────────────────────┼───────────┘
                      ▼
              ┌─ 볼륨 ──────┐
              │ 실제 데이터  │ ← 남음
              └─────────────┘
```

**문법은 전부 `왼쪽:오른쪽` = `바깥:안쪽`**

```yaml
ports: "3306:3306" # 내 맥 : 컨테이너 안
volumes: "mysql-data:/var/lib/mysql" # 볼륨 이름 : 컨테이너 안 경로
```

- 왼쪽(볼륨 이름) — **내가 짓는다**
- 오른쪽(경로) — **그 프로그램이 이미 정해둔 것**을 찾아서 적는다
  (mysql `/var/lib/mysql` · postgres `/var/lib/postgresql/data` · redis `/data`)

**증명한 방법** — `docker diff`로 컨테이너 변경 목록을 보면 볼륨에 쓴 파일은 안 나온다.
그 쓰기가 컨테이너 층을 거치지 않았다는 뜻.

**Compose는 볼륨 이름 앞에 프로젝트명을 붙인다** (`fortyall-desk_mysql-data`).
프로젝트마다 `mysql-data` 라는 흔한 이름을 써도 충돌하지 않게 하려는 것.

### 2-3. `ddl-auto`

| 값            | 동작                                                     | 쓰는 곳                       |
| ------------- | -------------------------------------------------------- | ----------------------------- |
| `none`        | 아무것도 안 함                                           | 스키마를 SQL로 직접 관리할 때 |
| `validate`    | 엔티티와 테이블이 맞는지 **검사만**. 어긋나면 앱이 안 뜸 | **운영**                      |
| `update`      | 테이블·컬럼 **추가만**                                   | **로컬 개발** ← 지금          |
| `create-drop` | 뜰 때 만들고 내려갈 때 지움                              | 테스트                        |

**`update`의 함정 — 더하기만 하고 빼기를 안 한다.**

| 상황        | 동작                                    |
| ----------- | --------------------------------------- |
| 필드 추가   | 컬럼 추가 ✅                            |
| 필드 삭제   | **아무것도 안 함** — 컬럼이 그대로 남음 |
| 타입 변경   | **아무것도 안 함**                      |
| 컬럼명 변경 | 새 컬럼 추가 + 옛 컬럼 잔존             |

컬럼을 지우는 건 데이터를 지우는 것이라 Hibernate가 자동으로 판단하지 않는다.

**Flyway 도입 시점 — D15 (W3 초입)**
D14에 엔티티 12개가 확정되면 그때 베이스라인 하나로 도입한다. 그 전에 넣으면
엔티티가 바뀔 때마다 마이그레이션 스크립트를 손으로 써야 해서 JPA 학습 시간을 잡아먹는다.

```yaml
# D15 이후 운영 설정
spring:
  jpa:
    hibernate:
      ddl-auto: validate # 검사만
  flyway:
    enabled: true # 스키마 변경은 여기서만
```
