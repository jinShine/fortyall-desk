# 엔티티 설계 — 12개 테이블과 그 이유

> 이 문서는 "왜 이렇게 쪼갰는가"를 담는다. 각 분리마다 **그렇게 안 했을 때 깨지는 구체적 상황**이 붙어 있다.
> 등장인물은 기획서 시나리오의 실제 인물이다.

## 등장인물

| 인물 | 상황 |
|---|---|
| 김대표 | 그린코트테니스 원장. 관리자면서 코치도 한다 |
| 박준석 | 코치 |
| 김혜원 | 정기 회원 (매주 화 20:00), 앱 사용 |
| 김서연 | 정기 회원, **주 2회** (화·목). 6주 해외 출장 예정 |
| 김상진·김아들 | **부자(父子) 2인 레슨.** 토 11:00 한 자리를 공유 |
| 윤다리 | **A센터 정기 회원이면서 B센터 회차제 회원** |
| 오할머니 | 앱을 안 쓴다. 관리자가 대신 관리 |

# 전체 그림

```
[1층 · 사람과 센터]
   account ──1:N──> center_membership <──N:1── center
                        └──1:N──> membership_role

[2층 · 돈과 권리]
   center ──1:N──> lesson_product ──1:N──> lesson_pass ──1:N──> lesson_pass_ledger
                                         ↑ N:1
                                    center_membership

[3층 · 정기 이용]
   center_membership ──1:N──> recurring_enrollment ──1:N──> schedule_assignment
                                                        ↑ N:1
                                              recurring_schedule
                                              (coach_membership_id → center_membership)

[4층 · 실제 수업]
   recurring_schedule ──1:N──> lesson ──1:N──> lesson_participant
                                                  ├── center_membership_id
                                                  └── lesson_pass_id
```

**층이 올라갈수록 구체적이다.** 1층은 "누가 있나", 4층은 "8월 12일 화요일 20시에 무슨 일이 있었나".

# 1층 · 사람과 센터

## ① center — 센터(테넌트)

담는 사실: **"그린코트테니스라는 센터가 있고, 이런 정책으로 운영된다"**

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `name` | 센터 이름 |
| `status` | ACTIVE / SUSPENDED / TERMINATED |
| `booking_window_days` | 셀프 예약 가능 범위 (기본 30일) |
| `renewal_grace_days` | 재등록 유예 일수 (기본 7일) |

정책값을 컬럼으로 둔 이유 — 센터마다 다르게 설정할 수 있어야 한다. 코드에 `30`을 박으면
센터별 조정이 불가능하다. **차이를 코드가 아니라 데이터로 흡수한다.**

FK: 없음. 이 테이블이 모든 것의 뿌리다.

## ② account — 사람(로그인 단위)

담는 사실: **"010-1234-5678 이라는 번호로 로그인하는 사람이 있다"**

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `login_phone` | 로그인 번호. **유니크** |
| `status` | ACTIVE / WITHDRAWN |

FK: 없음.

## ③ center_membership — 센터별 소속  ★ 가장 중요한 분리

담는 사실: **"윤다리이라는 사람이 A센터에서는 정기 회원이다"**

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `account_id` | FK → account. **null 가능** |
| `center_id` | FK → center. 필수 |
| `display_name` | 이 센터에서 부르는 이름 |
| `contact_phone_number` | **센터 연락처.** 로그인 번호와 별개 |
| `status` | PENDING / ACTIVE / DORMANT / WITHDRAWN |

### 왜 account와 membership을 나눴나 — 윤다리

윤다리은 A센터 정기 회원이면서 B센터 회차제 회원이다. 한 테이블로 표현해보면:

```
member
│ 윤다리 │ 010-1234-5678 │ A센터?B센터? │ ← 한 칸에 두 개
```

**한 사람이 여러 센터에 속한다.** 그래서 "사람"과 "센터별 소속"을 나눈다.

```
account:     윤다리 (010-1234-5678)          ← 사람은 하나
center_membership:  윤다리@A센터 / 윤다리@B센터      ← 소속은 둘
```

### 왜 account_id 가 null 가능인가 — 오할머니

기획서 6.2: **공개 가입이 없다.** 관리자가 회원을 먼저 만들고, 회원이 첫 OTP 인증으로 활성화한다.

```
1. 김대표가 오할머니를 등록  → center_membership 생성, account_id = null, status = PENDING
2. 오할머니가 폰으로 인증     → account 연결, status = ACTIVE
3. 오할머니가 앱을 안 쓴다면  → account_id 는 영원히 null. 그래도 관리는 된다
```

앱을 안 쓰는 회원도 완전히 지원해야 하므로 `account_id` 는 null이어야 한다.

### 왜 login_phone 과 contact_phone 을 나눴나 — 테넌트 경계

윤다리이 번호를 바꿨다. A센터 관리자가 고쳐준다면?

- 한 컬럼이면 → **A센터 관리자의 수정이 B센터 로그인까지 바꿔버린다**
- 나눠두면 → A센터 관리자는 `center_membership.contact_phone_number`(알림 발송용)만 수정.
  `account.login_phone`은 본인만 변경 (기존+새 번호 이중 인증)

### ★ 모든 도메인 데이터가 center_membership 에 붙는다

수업권·정기등록·레슨을 `accounts`에 붙이면:

```
account: 윤다리
   └── lesson_pass (10회)   ← A센터 것인가 B센터 것인가?
```

**B센터에서 산 수업권으로 A센터 레슨을 예약할 수 있게 된다.** 돈은 B센터가 받았는데
코치 시간은 A센터가 쓴다. 실제 서비스면 정산 사고다.

그래서 규칙: **로그인 정보만 account, 나머지는 전부 center_membership.**

## ④ membership_role — 역할

담는 사실: **"김대표는 이 센터에서 관리자이면서 코치다"**

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `center_membership_id` | FK → center_membership |
| `role` | ADMIN / COACH / MEMBER |

유니크: `(center_membership_id, role)` — 같은 역할을 두 번 부여할 수 없다.

### 왜 컬럼이 아니라 테이블인가 — 김대표

```
center_membership
│ 김대표 │ ADMIN, COACH │ ← 한 칸에 두 개
```

소규모 센터는 원장이 코치를 겸한다 (기획서 3.3 "Role을 복수로 가질 수 있다").
**값이 하나가 아니면 컬럼이 아니라 테이블이다.**

### 왜 account 가 아니라 center_membership 에 붙나

역할은 센터마다 다르다. 윤다리은 A센터에서 회원, B센터에서 코치일 수 있다.
`accounts`에 붙이면 그게 표현되지 않는다.

> 이 테이블은 기획 초안(11개)에 없었다. "Role 복수 보유"를 만족시키려면 필요하다는 걸
> 설계 단계에서 발견해 추가했다.

# 2층 · 돈과 권리

## ⑤ lesson_product — 상품 카탈로그

담는 사실: **"이 센터는 20분 10회권을 40만원에 판다"**

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `center_id` | FK → center |
| `name` | "20분 10회권" |
| `duration_minutes` | 레슨 길이 (20/30/60) |
| `max_participants` | 인원 (1인/2인) |
| `session_count` | 횟수 |
| `validity_days` | 유효기간 |
| `price` | 가격. **DECIMAL** |
| `is_active` | 판매 중인가 |

### 왜 상품 종류마다 테이블을 만들지 않나

20분권, 30분권, 2인권, 체험권을 각각 테이블로 만들면 종류가 늘 때마다 코드를 고쳐야 한다.
**속성 조합으로 표현하면 데이터만 추가하면 된다** (기획서 4.3 "차이를 코드가 아니라 데이터로 흡수").

체험 레슨도 특별 취급이 없다 — `session_count = 1` 인 상품일 뿐이다.

### price 를 DECIMAL 로 두는 이유

`double`은 0.1을 정확히 표현하지 못한다. 돈 계산에서 오차가 누적되면 정산이 안 맞는다.
**돈은 항상 `DECIMAL`(자바 `BigDecimal`).**

## ⑥ lesson_pass — 수업권  ★ 스냅샷의 사례

담는 사실: **"김혜원이 8월 1일에 20분 10회권을 40만원에 샀다"**

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `center_membership_id` | FK → center_membership |
| `lesson_product_id` | FK → lesson_product |
| `product_name` | **복사** — "20분 10회권" |
| `total_sessions` | **복사** — 10 |
| `paid_amount` | **복사** — 실제 받은 금액 |
| `start_date` / `end_date` | 유효기간 |
| `status` | PENDING / ACTIVE / EXHAUSTED / EXPIRED / CANCELLED |

**⚠️ 잔여 횟수 컬럼이 없다.** (⑦에서 설명)

### 왜 lesson_product 를 참조하는데 값을 또 복사하나

정규화 원칙대로면 `lesson_product_id` 만 두고 조인하면 된다. 그런데:

```
6개월 뒤 원장님이 가격을 40만 → 50만으로 올린다
   → 참조만 뒀다면, 작년에 40만원에 판 수업권이 소급해서 50만원이 된다
```

**과거는 변하면 안 된다.** 판매 시점의 계약 조건은 그 시점에 얼어붙어야 한다.

판단 기준:

| 이 값은 | 처리 |
|---|---|
| 지금 상태를 묻는 것 (센터 이름, 코치 이름) | **참조** — 바뀌면 같이 바뀌어야 |
| 그때의 사실 (판매 가격, 계약 횟수) | **스냅샷** — 얼어붙어야 |

### 재등록은 항상 새 Pass

기존 Pass에 횟수를 더하지 않는다. **UI에서 "충전"이라고 부르더라도 내부는 새 Pass 발급.**
안 그러면 40만원에 산 10회와 50만원에 산 10회가 한 Pass에 섞여서, 나중에
"이 회차는 어느 조건으로 판 것인가"에 답할 수 없다.

## ⑦ lesson_pass_ledger — 원장(Ledger)  ★ 이 프로젝트의 심장

담는 사실: **"8월 13일에 출석해서 1회 차감됐다"**

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `lesson_pass_id` | FK → lesson_pass |
| `entry_type` | ISSUE / ATTEND / NO_SHOW / LATE_CANCEL / RESTORE / ADJUST / EXPIRE / ... |
| `session_delta` | 증감. 발급 +10, 출석 −1, 복구 +1 |
| `lesson_participant_id` | 어느 레슨에서 발생했나 (추적용) |
| `reason` | 사유 |

### 왜 잔여를 컬럼으로 저장하지 않나 — 김혜원의 전화

> "제 잔여가 왜 3회예요? 저 네 번밖에 안 왔는데요."

**컬럼을 보고 있으면** 할 말이 `"3회 맞으세요"` 뿐이다. 답은 맞지만 근거가 없다.

**원장을 보고 있으면:**

```
┌──────────┬──────┬──────┐
│ 사유     │ 증감 │ 잔액 │
├──────────┼──────┼──────┤
│ 발급     │  +10 │   10 │  8/1  40만원 승인
│ 출석     │   -1 │    9 │  8/13
│ 노쇼     │   -1 │    8 │  8/27
│ 노쇼복구 │   +1 │    9 │  8/28  사정 확인 후
│ 조정     │   -1 │    8 │  정산 보정
└──────────┴──────┴──────┘
잔여 = 증감의 합
```

"8월 1일에 10회 넣었고, 13일 출석 −1, 27일 노쇼 −1, 28일에 사정 말씀하셔서 복구 +1..."

### 결정적인 이유 — 되돌릴 수 없다

6개월 뒤 "이력이 필요하네" 싶어도 **지나간 6개월의 이력은 어디에도 없다.**
특히 이 서비스는 노쇼 차감을 관리자가 복구할 수 있어서 잔여가 줄었다 늘었다 한다.
컬럼 하나면 "어제 2회였는데 오늘 왜 3회지?"에 아무도 답할 수 없다.

### 잔여 / 확보 / 사용 3종 (기획서 4.1)

| | 정의 | 어디서 오나 |
|---|---|---|
| 잔여 | 남은 횟수 | `SUM(lesson_pass_ledger.session_delta)` |
| 확보 | 셀프 예약이 잡아둔 횟수 | `lesson_participant.is_pass_reserved = true` 개수 |
| 추가 예약 가능 | 잔여 − 확보 | 계산 |

**고정 레슨은 확보하지 않는다.** 매주 자동 생성되고 출석 시점에 차감한다.
잔여가 부족해도 레슨은 생성되며, 충전 유예·외상이 이를 받는다. 이 비대칭이 유예 구조와 맞물린다.

# 3층 · 정기 이용  ★ 가장 어려운 층

## ⑧ recurring_schedule — 고정 스케줄 규칙

담는 사실: **"매주 화요일 20시에 박준석 코치의 20분 레슨 자리가 있다"**

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `center_id` | FK → center |
| `coach_membership_id` | FK → **center_membership** (코치) |
| `duration_minutes` | 레슨 길이. **상품을 참조하지 않는다** |
| `day_of_week` | 요일 |
| `start_time` | 시각 |
| `status` | ACTIVE / TERMINATED |

### 코치도 center_membership 이다

코치를 위한 별도 테이블이 없다. 코치도 사람이고 센터에 소속돼 있으니 `center_memberships` 한 줄이다.
역할이 COACH일 뿐이다.

**한 테이블(center_membership)을 회원 쪽에서도 코치 쪽에서도 가리키게 된다.** 문제없지만
컬럼 이름으로 역할을 구분해야 한다 — `coach_membership_id`. 안 그러면 6개월 뒤 본인도 헷갈린다.

### 왜 상품(lesson_product)을 참조하지 않나

스케줄이 상품을 가리키면 이런 질문이 생긴다.

> 화요일 20시 자리는 **10회권 전용**인가? 20회권 전용인가? 체험권 전용인가?

말이 안 된다. 자리는 자리일 뿐이고, 어떤 수업권으로 오든 20분 레슨이다.

스케줄이 상품에서 필요로 했던 값은 **레슨 길이 하나**뿐이었다 (종료 시각 계산용).
그래서 참조를 끊고 `duration_minutes` 를 직접 갖는다.

**인원(max_participants)도 필요 없다.** 2인 레슨은 `schedule_assignments` 에 **줄이 2개**
있는 것으로 표현된다. 인원은 배정 개수가 결정한다.

### ★ 이 테이블에 없는 것

- **회원이 없다** → `schedule_assignments` 로 빠졌다
- **홀드가 없다** → `recurring_enrollments` 로 빠졌다

**"스케줄은 시간만 안다. 누가 다니는지, 쉬는지는 모른다."** 이게 경계다.

## ⑨ recurring_enrollment — 정기 등록  ★ 가장 발견하기 어려운 테이블

담는 사실: **"김서연의 정기 이용 관계가 현재 홀드 상태이고 4월 12일에 복귀한다"**

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `center_membership_id` | FK → center_membership |
| `current_pass_id` | FK → lesson_pass. 지금 차감에 쓰는 Pass |
| `next_pass_id` | FK → lesson_pass. 선결제해 둔 다음 Pass |
| `status` | ACTIVE / HOLD / GRACE / TERMINATED |
| `resume_date` | 홀드 복귀일 |
| `grace_end_date` | 재등록 유예 종료일 |

### 왜 이 테이블이 필요했나 — 두 번의 실패

**시도 A — 홀드를 recurring_schedule 에 둔다**

```
recurring_schedule
│ 1 │ 토 11:00 │ 홀드 │ ← 김상진가 출장
```

김상진와 김아들이 **한 자리를 공유**한다. 스케줄에 홀드를 걸면
**출장 안 간 김아들까지 수업이 멈춘다.** ❌

**시도 B — 홀드를 schedule_assignment 에 둔다**

```
schedule_assignment
│ 3 │ 화 20:00 │ 김서연 │ 홀드 │ 2026-04-12 │
│ 4 │ 목 19:00 │ 김서연 │ 홀드 │ 2026-04-12 │  ← 같은 사실이 두 줄에 복사
```

2인 문제는 풀리는데, **김서연은 주 2회**라 화·목이 각각 한 줄이다.
복귀일을 4/20으로 미루면서 한 줄만 고치면
**"화요일은 홀드인데 목요일은 활성"** 인 유령 상태가 된다. ⚠️

**질문을 바꾼다**

```
홀드는 "화요일 참가"에 대한 사실인가?              → 아니다
홀드는 "목요일 참가"에 대한 사실인가?              → 아니다
홀드는 "김서연의 정기 이용 관계 전체"에 대한 사실인가? → 그렇다
```

그런 단위가 테이블에 없었다. **그래서 만들었다.**
홀드 날짜가 한 곳에만 있으니 복귀일을 바꾸면 화·목이 함께 따라온다.

### 여기서 나오는 규칙

> **같은 값이 여러 줄에 복사되는 게 보이면, 아직 이름을 붙이지 않은 단위가 숨어 있다는 신호다.**

중복은 추상적인 잘못이 아니라 **경계를 잘못 그었다는 구체적 증거**다.

## ⑩ schedule_assignment — 스케줄 참가자

담는 사실: **"김서연의 정기 등록이 화요일 20시 스케줄에 참가한다"**

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `recurring_schedule_id` | FK → recurring_schedule |
| `recurring_enrollment_id` | FK → recurring_enrollment |
| `is_active` | 참가 중인가 |

유니크: `(recurring_schedule_id, recurring_enrollment_id)`

### 왜 중간 테이블인가

```
스케줄 1개(토 11시)에 회원 몇 명? → 여러 명 (김상진 + 김아들)
회원 1명은 스케줄 몇 개?          → 여러 개 (주 2회면 화 + 목)
```

**양쪽 다 여러 개 = N:M.** FK로 표현할 수 없으니 중간 테이블이 필요하다.

### 이 구조 하나로 전부 표현된다

```
1인 레슨   → 1줄
2인 레슨   → 같은 스케줄에 2줄  (김상진, 김아들)
주 2회     → 같은 정기등록이 다른 스케줄에 2줄  (김서연 화, 목)
한 명 중단 → 그 줄만 active = false
```

특수 케이스를 위한 별도 코드가 없다. **구조가 하나다.**

### center_membership_id 를 두지 않는 이유

`recurring_enrollments` 를 타고 가면 회원을 알 수 있다.
두 군데 적으면 어긋날 수 있으니 **파생 가능한 FK는 중복 저장하지 않는다.**

# 4층 · 실제 수업

## ⑪ lesson — 발생한 레슨 1건

담는 사실: **"8월 12일 화요일 20시에 박준석 코치의 레슨이 있다"**

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `center_id` | FK → center |
| `recurring_schedule_id` | FK → recurring_schedule. **null 가능** |
| `coach_membership_id` | FK → center_membership |
| `lesson_date` / `start_time` / `end_time` | 시각 |
| `source_type` | RECURRING / SELF_BOOKED |
| `is_rescheduled` | 회원이 개별 이동했나 |

유니크 2개:
- `(recurring_schedule_id, lesson_date)` — **Materializer 멱등성.** 배치를 두 번 돌려도 레슨은 1개
- `(coach_membership_id, lesson_date, start_time)` — **동시 예약 방어.** 한 코치의 같은 시각에 레슨은 하나

### 왜 규칙만 두지 않고 레슨을 미리 만드나

`recurring_schedules` 만 있으면 "매주 화 20시"라는 규칙은 알지만
**8월 12일에 실제로 무슨 일이 있었는지**는 담을 곳이 없다. 레슨마다 출석·차감·변경 상태가 붙는다.

그래서 미래 레슨을 미리 생성한다(**materialize**). 매일 rolling으로 90일치를 유지한다.

**90일인 이유** — 셀프 예약 범위(Booking Window, 최대 60일)보다 커야 한다.
안 그러면 회원이 조회하는 범위에 정기 레슨이 아직 없어서, 그 자리를 "빈 시간"으로
오인해 다른 회원이 예약하는 **이중 예약**이 생긴다.

### recurring_schedule_id 가 null 가능한 이유

셀프 예약으로 생긴 레슨은 고정 스케줄에서 온 게 아니다.

## ⑫ lesson_participant — 레슨 참가자  ★ 출석이 사는 곳

담는 사실: **"김혜원이 8월 12일 레슨에 출석해서 55번 수업권에서 1회 차감됐다"**

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `lesson_id` | FK → lesson |
| `center_membership_id` | FK → center_membership |
| `lesson_pass_id` | FK → lesson_pass. **어느 지갑에서 깎았나** |
| `status` | SCHEDULED / ATTENDED / EARLY_CANCEL / LATE_CANCEL / NO_SHOW / SUSPENDED |
| `is_pass_reserved` | 셀프 예약이 확보한 건가 |

유니크: `(lesson_id, center_membership_id)` — 한 레슨에 같은 회원이 두 줄 들어갈 수 없다

### 왜 출석 상태가 lesson 이 아니라 여기 있나 — 김상진·김아들

2인 레슨에서 **아버지는 출석했는데 아들은 노쇼**일 수 있다.

```
lesson_participant
┌────┬───────────┬─────────┬────────────────┬────────┐
│ id │ lesson_id │ 회원    │ lesson_pass_id │ status │
├────┼───────────┼─────────┼────────────────┼────────┤
│ 1  │    100    │ 김상진  │       55       │ 출석   │ → 55번에서 −1
│ 2  │    100    │ 김아들  │       56       │ 노쇼   │ → 56번에서 −1
└────┴───────────┴─────────┴────────────────┴────────┘
      같은 레슨      다른 사람    각자의 지갑     각자의 상태
```

출석을 `lessons`에 두면 이게 표현되지 않는다. **출석은 레슨의 사실이 아니라 참가자의 사실이다.**

### lesson_pass_id 가 왜 필요한가

회원이 수업권을 2장 갖고 있을 수 있다 (20분 10회권 + 체험 1회권).
**어느 장에서 깎았는지 기록해야** 나중에 노쇼를 복구할 때 원래 자리로 되돌릴 수 있다.

# 정리 — 경계를 정한 기준 4개

| 기준 | 적용 사례 |
|---|---|
| **값이 하나가 아니면 테이블** | `membership_roles` (원장 = 관리자+코치) |
| **양쪽 다 여러 개면 중간 테이블** | `schedule_assignments` (2인 레슨 × 주 2회) |
| **이 사실은 무엇에 대한 사실인가** | `recurring_enrollments` (홀드), `lesson_participants` (출석) |
| **계산할 수 있으면 저장하지 않는다** | 잔여 = `SUM(session_delta)`, 빈 시간 = 근무 − 예약 |

여기에 예외 하나:

| | |
|---|---|
| **과거의 사실은 복사한다** | `lesson_passes` 의 가격·횟수 스냅샷 |

계산 가능한 값은 저장하지 않지만, **그때의 사실**은 지금 값으로 계산해선 안 된다.
가격이 바뀌면 과거 계약이 소급 변경되기 때문이다.

# 층별 책임 요약 (기획서 12장 원칙 6)

| 테이블 | 책임 | 담지 않는 것 |
|---|---|---|
`recurring_schedules` | 시간·슬롯 규칙의 생명주기 | 회원, 홀드 |
`recurring_enrollments` | 회원별 정기 생명주기 (홀드·유예·승계) | 시간, 요일 |
`lesson_passes` | 이용 권리·잔액 | 언제 쓰는지 |
`lessons` | 실제 발생한 수업 | 규칙 |

**이 4분할이 설계의 핵심이다.** 하나라도 섞이면 위의 반례들이 깨진다.
