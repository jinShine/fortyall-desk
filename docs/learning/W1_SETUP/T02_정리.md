## 2. 테스트는 왜 H2를 쓰나

|            | 운영 · 로컬        | 테스트                 |
| ---------- | ------------------ | ---------------------- |
| DB         | **MySQL (Docker)** | **H2 인메모리**        |
| 실행 위치  | 내 맥 / EC2        | 내 맥 / GitHub Actions |
| 데이터     | 남아야 한다        | **매번 깨끗해야 한다** |
| `ddl-auto` | `update`           | `create-drop`          |

**테스트는 매번 깨끗한 상태에서 시작해야 한다.** 앞 테스트가 남긴 데이터가 뒤 테스트에
영향을 주면 "혼자 돌리면 통과하는데 전체로 돌리면 실패"하는 상황이 생긴다.

H2는 자바 프로세스 안에서 도는 DB다. 설치도 컨테이너도 없이 앱이 뜰 때 메모리에
만들어지고 끝나면 사라진다. 그래서 CI(GitHub Actions)에서도 DB 없이 테스트가 돈다.

**그래서 `src/test/resources/application.yaml` 을 만들었다.**

```yaml
spring:
  datasource:
    url: jdbc:h2:mem:fortyall-test;MODE=MySQL;DB_CLOSE_DELAY=-1
    driver-class-name: org.h2.Driver
    username: sa
    password:
  jpa:
    hibernate:
      ddl-auto: create-drop
```

- 테스트를 돌릴 때 `src/test/resources` 가 `src/main/resources` 보다 **앞에** 놓인다.
  같은 이름의 파일이 양쪽에 있으면 테스트 쪽이 이긴다. 운영 설정을 안 건드리고 분리할 수 있다.
- `MODE=MySQL` — H2가 MySQL 방언을 흉내 내게 한다
- `DB_CLOSE_DELAY=-1` — 마지막 연결이 끊겨도 메모리에서 DB를 지우지 않는다

**대가**: H2와 MySQL은 다른 DB라 SQL 방언이 미묘하게 다르다. MySQL에선 되는데 H2에선
안 되는 쿼리가 나올 수 있다. 그 경계를 넘어야 하면 Testcontainers(테스트용 진짜 MySQL 컨테이너)로
갈아탄다. 지금 단계에선 과하다.

**검증 방법**: `docker compose stop` 한 상태에서 `./gradlew test` 가 통과하면 분리 성공.

## 3. `@Entity` — 클래스와 테이블을 잇는다

```java
@Entity
@Table(name = "center")
public class Center extends BaseEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 100)
    private String name;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private CenterStatus status = CenterStatus.ACTIVE;
}
```

| 애노테이션                     | 역할                                                   |
| ------------------------------ | ------------------------------------------------------ |
| `@Entity`                      | 이 클래스는 테이블 하나에 대응한다                     |
| `@Table(name = ...)`           | 테이블 이름 명시. 생략하면 클래스명을 스네이크케이스로 |
| `@Id`                          | 기본키                                                 |
| `@GeneratedValue(IDENTITY)`    | 번호는 DB의 auto_increment가 매긴다                    |
| `@Column(nullable = false)`    | NOT NULL 제약을 **DB에** 건다                          |
| `@Enumerated(EnumType.STRING)` | enum을 글자 그대로 저장                                |

### `@GeneratedValue` 전략은 사실상 하나

| 전략       | MySQL에서                        |
| ---------- | -------------------------------- |
| `IDENTITY` | ✅ auto_increment                |
| `SEQUENCE` | MySQL에 시퀀스가 없다            |
| `TABLE`    | 별도 키 테이블. 느려서 안 쓴다   |
| `AUTO`     | JPA가 알아서 고름. 예측이 어렵다 |

`IDENTITY`는 **ID를 DB가 만들어주므로 `save()` 하는 순간 INSERT가 바로 나간다.**
JPA는 원래 쓰기를 모아뒀다 한 번에 보내지만(쓰기 지연), ID를 알아야 영속성 컨텍스트에
넣을 수 있어서 미룰 수 없다.

### `EnumType.STRING` 을 반드시 쓰는 이유

이걸 빼면 기본값이 `ORDINAL` — enum의 **순서를 숫자로** 저장한다.

```
ACTIVE=0, SUSPENDED=1, TERMINATED=2
```

나중에 enum 중간에 값을 하나 끼워 넣으면

```java
enum CenterStatus { ACTIVE, PENDING, SUSPENDED, TERMINATED }
                            ^^^^^^^ 추가
```

`SUSPENDED` 가 1에서 2로 바뀐다. **DB에 저장된 1들이 전부 의미가 달라진다.**
정지 상태였던 센터가 하루아침에 대기 상태가 되고, 되돌릴 방법이 없다.

`STRING` 이면 `'SUSPENDED'` 라고 글자로 들어가서 이런 일이 없다. 저장 공간을 조금 더
쓰는 대신 안전을 산다.

### `@Column(nullable = false)` 를 왜 DB 제약으로 거나

자바 코드에서만 검사하면 다른 경로(직접 SQL, 배치, 다른 애플리케이션)로 들어오는 값을
못 막는다. **DB가 마지막 방어선이다.**

## 4. `@MappedSuperclass` — 상속인데 테이블이 안 생긴다

`createdAt` · `updatedAt` 은 12개 엔티티에 전부 들어간다. 매번 복사하면 관리가 안 된다.

```java
@Getter
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {

    @CreatedDate
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;
}
```

|        | `@Entity`          | `@MappedSuperclass`         |
| ------ | ------------------ | --------------------------- |
| 테이블 | **생긴다**         | **안 생긴다**               |
| 역할   | 자기 테이블에 대응 | 필드를 자식 테이블에 심는다 |

`base_entity` 테이블은 만들어지지 않고, `center` 테이블에 `created_at` · `updated_at`
컬럼이 생긴다. 자식이 필드를 물려받는 것이지, 부모가 별도 테이블로 존재하는 게 아니다.

`abstract` 로 둔 이유 — 이 클래스 자체로 객체를 만들 일이 없다.

## 5. `@EnableJpaAuditing` — 없으면 `@CreatedDate` 가 null

`@CreatedDate` 만 붙이면 **값이 채워지지 않는다.** 세 개가 다 있어야 동작한다.

```
① @CreatedDate                                    필드에
② @EntityListeners(AuditingEntityListener.class)  BaseEntity에
③ @EnableJpaAuditing                              설정에  ← 스위치
```

`AuditingEntityListener` 가 저장 직전에 끼어들어 시각을 넣는데, **그 기능 자체가
기본적으로 꺼져 있다.** `@EnableJpaAuditing` 이 스위치다.

**`@EnableJpaAuditing` 을 메인 클래스로 옮긴다.**

```java
@EnableJpaAuditing
@SpringBootApplication
public class FortyallDeskApplication { ... }
```

## 6. 면접 질문

### Q1. enum을 DB에 어떻게 저장하셨나요?

**의도** — `ORDINAL` 의 위험을 아는지. 실무에서 실제로 사고가 나는 지점.

> `@Enumerated(EnumType.STRING)` 으로 문자열 저장했습니다. 기본값인 `ORDINAL` 은 enum의
> 순서를 숫자로 저장해서, 나중에 enum 중간에 값을 추가하면 기존 데이터의 의미가 전부
> 바뀝니다. 저장 공간을 조금 더 쓰는 대신 안전을 택했습니다.

### Q2. `ddl-auto` 는 환경별로 어떻게 쓰셨나요?

**의도** — 편한 설정을 그냥 쓴 사람인지, 운영을 생각해본 사람인지.

> 로컬은 `update`, 테스트는 `create-drop`, 운영은 `validate` 로 나눴습니다. `update` 는 컬럼
> 추가만 하고 삭제·타입 변경은 하지 않아서, 필드를 지워도 컬럼이 NOT NULL로 남아 저장이
> 실패하는 걸 직접 확인했습니다. 운영은 `validate` 로 두고 스키마 변경은 Flyway로 관리합니다.
