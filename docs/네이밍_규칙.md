# 테니스 레슨 관리 SaaS — 엔티티/컬럼 네이밍 개선안

> 기준 문서: 기존 **엔티티 설계 12개 테이블**
>
> 목표는 영어를 어렵게 만드는 것이 아니라, **테이블명과 컬럼명만 읽어도 역할을 어느 정도 추측할 수 있게 만드는 것**이다.
>
> 기존 엔티티의 책임과 관계는 최대한 유지하되, 이름이 모호한 부분은 더 쉬운 영어로 바꿨다.

---

# 0. 네이밍 원칙

이 프로젝트에서는 아래 원칙으로 이름을 통일하는 것을 추천한다.

## 0.1 너무 넓은 단어는 피한다

```text
membership
product
transaction
```

이런 이름은 틀리지는 않지만 의미 범위가 너무 넓다.

대신:

```text
center_membership
lesson_product
lesson_pass_ledger
```

처럼 **무엇에 대한 데이터인지 이름에 드러내는 것**이 좋다.

---

## 0.2 반복되는 스케줄은 `recurring`

기존:

```text
standing_schedule
regular_enrollment
```

`standing`, `regular`도 영어로는 가능한 표현이지만 처음 보면 의미를 바로 알기 어렵다.

이 프로젝트에서 말하는 핵심은 **매주 반복되는 레슨**이므로:

```text
recurring_schedule
recurring_enrollment
```

처럼 `recurring`으로 통일한다.

---

## 0.3 boolean은 가능하면 `is_` 사용

기존:

```text
active
reserved
manually_modified
```

추천:

```text
is_active
is_pass_reserved
is_rescheduled
```

DB에서는 꼭 `is_`를 써야 하는 것은 아니지만,
학습 단계와 협업 가독성을 생각하면 **boolean이라는 사실이 바로 보이는 이름**이 편하다.

---

## 0.4 날짜는 의미가 보이도록 쓴다

애매한 이름:

```text
hold_until
grace_until
```

추천:

```text
resume_date
grace_end_date
```

`until`보다 **그 날짜에 실제로 무슨 일이 일어나는지** 보이는 이름을 선호한다.

---

## 0.5 `type`, `status`는 맥락이 충분하지 않으면 구체화한다

예:

```text
pass_transaction.type
```

보다:

```text
lesson_pass_ledger.entry_type
```

가 좋다.

반대로 테이블 자체가 충분히 명확하다면:

```text
lesson.status
membership.status
```

처럼 그냥 `status`를 사용해도 괜찮다.

# 5. `center_memberships`

기존:

```text
membership
```

추천:

```text
center_membership
```

## 의미

> 한 사람이 특정 센터에 소속되어 있는 관계

이 테이블은 이 프로젝트에서 매우 중요하다.

`membership`만 쓰면 흔히 다음 의미로 오해할 수 있다.

```text
회원권
구독 상품
멤버십 플랜
```

하지만 여기서는:

```text
윤다리 @ A센터
윤다리 @ B센터
```

같은 **센터별 소속**을 의미하므로 `center_memberships`이 훨씬 명확하다.

## 추천 컬럼

| 기존 | 추천 |
|---|---|
| `id` | `id` |
| `account_id` | `account_id` |
| `center_id` | `center_id` |
| `name` | `display_name` |
| `contact_phone` | `contact_phone_number` |
| `status` | `status` |

### 왜 `name` → `display_name`?

이 이름은 계정의 법적 이름/실명이라기보다
**해당 센터에서 관리하는 회원 이름**이라는 의미가 강하다.

따라서:

```text
name
```

보다:

```text
display_name
```

이 역할을 조금 더 잘 표현한다.

단, 서비스에서 무조건 실명을 저장한다면 `name`을 그대로 사용해도 좋다.

### 최종

```text
center_membership
─────────────────────────
id
account_id              nullable
center_id
display_name
contact_phone_number
status
created_at
updated_at
```

# 8. `lesson_passes`

기존 이름을 유지한다.

```text
lesson_pass
```

이 이름은 상당히 좋다.

## 의미

> 회원이 실제 구매해서 가지고 있는 수업권

`lesson_products`가 **판매 상품의 정의**라면,

`lesson_passes`는:

> 김혜원 회원이 2026년 8월 1일 실제로 구매한 10회권

을 의미한다.

## 추천 컬럼

| 기존 | 추천 |
|---|---|
| `id` | `id` |
| `membership_id` | `center_membership_id` |
| `product_id` | `lesson_product_id` |
| `product_name_snapshot` | `product_name` |
| `session_count_snapshot` | `total_sessions` |
| `paid_amount` | `paid_amount` |
| `valid_from` | `start_date` |
| `valid_until` | `end_date` |
| `status` | `status` |

## 스냅샷 컬럼 이름에 대한 추천

기존:

```text
product_name_snapshot
session_count_snapshot
```

설계 문서에서는 `snapshot`이라는 이름이 이해에 도움이 된다.

하지만 실제 DB에서는 굳이 모든 컬럼에 `_snapshot`을 붙이지 않아도 된다.

`lesson_passes` 자체가 이미 **구매 당시 계약을 보존하는 테이블**이기 때문이다.

따라서:

```text
product_name
total_sessions
paid_amount
```

만으로 충분히 자연스럽다.

### 추천안

```text
lesson_pass
─────────────────────────
id
center_membership_id
lesson_product_id

product_name
total_sessions
paid_amount

start_date
end_date
status

created_at
updated_at
```

### 왜 `session_count` → `total_sessions`?

`session_count`도 나쁘지 않지만 수업권 안에서는:

```text
total_sessions = 처음 계약한 총 횟수
```

라는 의미를 더 명확하게 보여준다.

잔여 횟수는 저장하지 않고 ledger에서 계산한다.

# 9. `lesson_pass_ledgers`

기존:

```text
pass_transaction
```

추천:

```text
lesson_pass_ledger
```

## 의미

> 수업권 횟수가 왜 늘거나 줄었는지 남기는 원장

이 테이블에서는 `transaction`이라는 표현을 피하는 것을 추천한다.

개발에서 transaction은 흔히:

```text
DB Transaction
결제 Transaction
```

의 의미로 많이 사용되기 때문이다.

현재 테이블의 본질은 **원장(Ledger)** 이다.

```text
발급      +10
출석       -1
노쇼       -1
복구       +1
관리자 조정 -1
```

따라서 `ledger`가 가장 정확하다.

## 추천 컬럼

| 기존 | 추천 |
|---|---|
| `id` | `id` |
| `lesson_pass_id` | `lesson_pass_id` |
| `type` | `entry_type` |
| `delta` | `session_delta` |
| `lesson_participant_id` | `lesson_participant_id` |
| `memo` | `reason` |

### 최종

```text
lesson_pass_ledger
─────────────────────────
id
lesson_pass_id
entry_type
session_delta
lesson_participant_id    nullable
reason                   nullable
created_at
```

## `entry_type` 예시

```text
ISSUE
ATTEND
NO_SHOW
LATE_CANCEL
RESTORE
ADJUST
EXPIRE
```

## 데이터 예시

```text
entry_type     session_delta
────────────────────────────
ISSUE          +10
ATTEND          -1
NO_SHOW         -1
RESTORE         +1
ADJUST          -1
```

이렇게 읽히면 `delta`보다 의미가 훨씬 명확하다.

```text
schedule_participant
```

```text
schedule_assignment
```

## 의미

> 어떤 정기 등록이 어떤 반복 스케줄에 배정되어 있는가

기존 `schedule_participant`는 아래 테이블과 이름이 너무 비슷하다.

```text
lesson_participant
```

하지만 실제 역할은 서로 다르다.

### `schedule_assignments`

```text
김서연의 정기등록
→ 화요일 20시 스케줄에 배정
```

### `lesson_participants`

# 13. `lessons`

기존 이름을 그대로 유지한다.

```text
lesson
```

## 의미

> 특정 날짜와 시간에 실제로 존재하는 레슨 한 건

`recurring_schedules`은 규칙이고,

`lessons`은 실제 발생 건이다.

```text
recurring_schedule
매주 화요일 20:00

        ↓ 생성

2026-08-04 20:00
```

| 기존 | 추천 |
|---|---|
| `id` | `id` |
| `center_id` | `center_id` |
| `standing_schedule_id` | `recurring_schedule_id` |
| `coach_membership_id` | `coach_membership_id` |

| `end_time` | `end_time` |

## `origin` → `source_type`

`origin`도 나쁜 이름은 아니지만,
이 컬럼의 실제 질문은:

> 이 레슨이 어디에서 만들어졌는가?

이다.

그래서:

```text
source_type
```

을 추천한다.

예:

```text
RECURRING
SELF_BOOKED
```

기존 `REGULAR`보다 `RECURRING`으로 용어를 통일하는 것을 추천한다.

## `manually_modified` → `is_rescheduled`

기존 설명은:

> 회원이 개별적으로 다른 시간으로 이동했는가

이므로 단순히 "수동 수정됨"보다:

```text
is_rescheduled
```

가 실제 비즈니스 의미에 더 가깝다.

### 최종

```text
lesson
─────────────────────────

center_id
recurring_schedule_id    nullable
coach_membership_id

lesson_date
start_time
end_time

created_at
updated_at
```

# 18. 추가로 검토하고 싶은 구조 — `lesson_type`

여기부터는 **단순 네이밍 변경이 아니라 구조 개선 제안**이다.

현재 `lesson_products`에는 다음 정보가 같이 들어간다.

```text
duration_minutes
max_participants

session_count
validity_days
price
```

그런데 이 값들은 사실 두 종류의 정보다.

### 실제 레슨 자체의 조건

```text
20분
1인
```

### 판매 조건

```text
10회
60일
400,000원
```

예를 들어:

```text
20분 10회권   400,000원
20분 20회권   750,000원
20분 체험권    30,000원
```

세 상품은 모두 **20분 1인 레슨**일 수 있다.

그런데 `recurring_schedules`이 `lesson_product_id`를 직접 바라보면:

> 이 화요일 20시 자리는 10회권 전용인가?  
> 20회권 전용인가?  
> 체험권 전용인가?

라는 애매한 문제가 생길 수 있다.

# 21. 가장 중요한 핵심만 다시 정리

이 설계에서 이름은 아래처럼 읽히면 성공이다.

```text
account
= 로그인하는 사람

center_membership
= 그 사람이 어느 센터에 소속되어 있는가

lesson_product
= 센터가 무엇을 판매하는가

lesson_pass
= 회원이 실제로 어떤 수업권을 샀는가

lesson_pass_ledger
= 그 수업권의 횟수가 왜 늘고 줄었는가

recurring_schedule
= 매주 언제 레슨 자리가 반복되는가

recurring_enrollment
= 회원이 정기 레슨을 이용하는 상태는 무엇인가

schedule_assignment
= 그 정기 회원이 어떤 요일/시간에 배정되어 있는가

lesson
= 특정 날짜에 실제 어떤 수업이 생겼는가

lesson_participant
= 그 수업에 누가 왔고 어떤 출석 상태였는가
```

**테이블 이름만 보고 위 문장이 자연스럽게 떠오르면 좋은 네이밍이다.**

이 기준에서는 기존 설계보다 아래 이름들이 특히 개선 효과가 크다.

```text
membership
→ center_membership

product
→ lesson_product

pass_transaction
→ lesson_pass_ledger

standing_schedule
→ recurring_schedule

regular_enrollment
→ recurring_enrollment

schedule_participant
→ schedule_assignment
```

# 22. 확정 사항 (2026-08-22)

## 채택
1~17장의 테이블·컬럼 네이밍 전부 채택한다.

## 수정하여 채택 — `recurring_schedules`

18~19장의 `lesson_type` 분리 대신 **더 작은 해결책**을 택한다.

```
recurring_schedule
  − lesson_product_id     제거
  + duration_minutes      추가
```

근거
1. 스케줄이 상품에서 필요로 하는 값은 **레슨 길이 하나**뿐이다 (종료 시각 계산용)
2. `max_participants` 는 불필요하다 — 2인 레슨은 `schedule_assignments` 줄이 2개인 것으로 표현된다
3. 테이블·조인이 하나씩 줄어든다. 22일 일정에서 실질적 차이다

## 보류 — `lesson_type`

레슨 종류가 늘어날 때(그룹 레슨, 코트 종류별 등) 값이 생긴다.
현재는 20/30/60분 × 1·2인 조합뿐이라 이르다. **9/12 이후 과제.**
